- 我做的假設與決策（含理由）：
  1. **`setCompleted` 實作為 `updateTodo(db, id, { isCompleted })` 的薄封裝**，而非獨立 SQL：兩者共用同一條 `UPDATE ... COALESCE` 語句（05 §3 原文本身也只給一條 update 查詢），符合「`isCompleted` 是設定目標狀態、非 toggle」（O-002）；任務卡文字把 `update` 與 `setCompleted` 並列為兩個操作，我理解為「對外提供的兩個呼叫入口」而非「兩套互斥的 SQL」，因為業務層（未來 WI-06）多半會分別呼叫「只改標題」與「只改完成狀態」兩種情境，各自命名一個函式更貼合呼叫端語意。
  2. **`createdAt` 型別維持 `Date`，不在本層轉字串**：BE-06 職責是 `snake_case ↔ camelCase` 命名轉換，05／ADR-0002 沒有要求本層再做型別轉字串；`Date` 經 Fastify 的 JSON 序列化會自動轉成 ISO 8601／含時區字串，滿足 BR-004／API 契約，且把「時間格式化」留給未來的 schema／序列化層（BE-04）避免職責重疊。
  3. **repository 函式以自訂最小介面 `Queryable`（只要求 `.query()`）注入，不直接匯入 `pg.Pool` 型別**：`pg.Pool`／`PoolClient` 皆結構相容 `Queryable`，但脫鉤後單元測試不需要真的建立或 mock 整個 `pg` 模組，只需一個陽春物件，這也是「無 DB 環境仍可單元測試 SQL 組裝」的關鍵設計。
  4. **`migrate.ts` 以 `pool.connect()` 取得的單一 `client` 執行 `BEGIN`/檔案全文/`INSERT INTO schema_migrations`/`COMMIT`**（而非直接對 `pool.query`），因為交易必須綁在同一條連線上；`pg.Pool.query()` 每次呼叫可能拿到池內不同連線，無法保證同一交易。
  5. **`tests/integration/todo-repository.test.ts` 的「500 筆同秒建立」測試以顯式 `INSERT ... (title, created_at) VALUES (...)` 直接指定相同 `created_at`**，而非真的在同一秒內連續呼叫 `createTodo` 500 次靠時間碰撞：後者在真實時鐘下幾乎不會產生完全相同的微秒級時間戳，測不到 tie-break；前者是唯一能可靠、快速、可重現地逼出「時間戳完全相同時 id 是否決定性 tie-break」這個規則的方法，且不違反任何約束（`created_at` 只在 `BEFORE UPDATE` 觸發器被保護，INSERT 時仍可顯式指定）。
  6. **新增 `tests/unit/todo-repository.test.ts`，超出任務卡原始 `outputs`**：依主控 agent 本輪指示（本機 Docker daemon 原判斷不可用時的應變方案）「同時提供一份不需 DB 的單元測試覆蓋 SQL 組裝與參數，讓 lint/build/unit 在無 DB 環境全綠」。雖然實測時 Docker 其實可用、整合測試也已對真實 DB 全綠，我仍保留這份單元測試：它與整合測試覆蓋的層次不同（純函式組裝 vs. 真實資料庫行為），對「阻擋級 CR 判準」還提供了一份可在 CI 無 DB 階段（例如僅跑 `test:unit` 的 lint job）就攔截回歸的自動化防線，屬於任務卡 acceptance 第 2 條「npm run lint 與相關測試全綠」精神範圍內的合理擴充。已同步在任務卡 `outputs` 補一行並在此說明，供 dev-tl 審核與 Leader 知悉，不視為隱藏變更。
