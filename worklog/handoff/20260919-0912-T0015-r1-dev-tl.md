### 對交接檔「假設與決策」逐條表態

1. **`WWW-Authenticate` 標頭自行組出，不用外掛的 `authenticate` 選項** —— **接受**。理由：`04_API規格.yaml` `components.responses.Unauthorized.headers.WWW-Authenticate` 與 ADR-0004 決定第 1 點皆逐字寫 `Basic realm="staging"`；外掛預設附加的 `charset="UTF-8"` 雖然合法，但會讓逐字比對的驗收（`curl -sSI ... | grep -i "^www-authenticate"`）與規格不一致。實測輸出正是 `Basic realm="staging"`，無多餘屬性。此決策同時涵蓋「外掛丟出的缺憑證錯誤」與「validate 丟出的帳密不符」兩條路徑，標頭行為一致，無遺漏分支。
2. **認證失敗一律經全域 error-handler 序列化，本檔不自行組 JSON** —— **接受**。這正是我在 T-0012 審核交接檔「下一步建議」第 1、2 點的交辦（不得在自己的 register 子情境內再呼叫 `setErrorHandler`），本卡確實遵守，全檔無 `setErrorHandler`。對於外掛原生的 `FST_BASIC_AUTH_MISSING_OR_BAD_AUTHORIZATION_HEADER`，我另行核驗其訊息為固定字面值 `Missing or bad formatted authorization header`，不含路徑、不含輸入原文、不含內部細節，經 `error-handler.ts` 的 `resolveCode(401) → E_UNAUTHORIZED` 分支序列化後仍完全符合 Error schema（實測本文已貼）。**不需要多包一層 `AppError`**，維持現狀。
3. **`registerBasicAuth`／`registerStatic` 為直接呼叫的一般函式，不另建巢狀子情境** —— **接受**，且這是本卡最關鍵的正確性決定。Fastify 的 hook 繼承是父→子單向：若 `onRequest` hook 掛在子情境內，之後以 `app.register()` 註冊的手足（static、WI-06 的 routes）不會繼承，靜態檔與 API 將完全不設防。與 WI-02 `registerErrorHandler` 作法一致，且實測 `/assets/api-client.js` 未帶憑證回 401，證明 hook 確實涵蓋後註冊的 static 路由。
4. **豁免用 `new URL(raw,"http://localhost").pathname` 取 pathname** —— **接受**（附但書，見「未完成／已知問題」第 1 點）。`URL` 是標準 API，正確處理查詢字串與 hash，且額外把 `//health` 正確排除在豁免之外（協定相對網址解析），比手動 `split("?")[0]` 更不易出錯。但書：`URL` 同時會做「點節段移除」，使 `/a/../health` 這類原始路徑被視為豁免；我已逐一實測其實際可達性，確認**不構成保護繞過**（詳見下）。
5. **靜態託管明確關閉快取（`no-store, private`）** —— **接受**，**不視為過度設計**。受保護內容被中介快取保留，之後未帶憑證的請求可能取得快取本文，這是 Basic Auth 站台的典型洩漏途徑；`no-store, private` 是成本為零的正確預設。雖非 WBS §1.5 明文驗收項，但與 SD §6.2「未帶憑證取 `public/` 資產同樣回 401」的規範意圖一致，不牴觸任何規格。**裁定：保留**，並已由 `auth-basic.test.ts` 第 11 條測試鎖住。
6. **`basic-auth.ts` 全檔改用 `//` 行註解以通過 `grep -nE "startsWith|RegExp|\*"` 無輸出的判準** —— **接受**。這是我在 WBS §1.5 寫下該 grep 判準時的疏漏：`\*` 會把 JSDoc 的 ` * ` 續行一併命中，屬判準本身的誤判面，不是實作缺陷。開發者選擇遷就判準而非修改判準（硬前提 1：不自行改規格），處置正確。**後續處理**：已列入「下一步建議」，建議 qa-cr 改用更精準的判準；WBS 文字本身不在本卡範圍，不於此修改。

- 下一步建議：
  1. **給 T-0016（WI-06，最重要）**：`[ANCHOR:routes]` 的所有 `app.inject()` 呼叫**必須帶 `headers: { authorization: ... }`**，否則會重演本卡發現的 401 問題（本卡收尾已示範寫法：`"Basic " + Buffer.from(\`${USER}:${PASSWORD}\`).toString("base64")`，由環境變數組出，不寫字面值）。curl 驗收一律加 `-u "$U:$P"`。
  2. **給 T-0016／qa-cr（零成本強化，非阻擋）**：若要讓豁免判斷與 Fastify 路由器的路徑觀點完全一致，可把 `extractPathname()` 改為「只剝除查詢字串與 hash、不做點節段移除」，例如取 `rawUrl` 中第一個 `?` 或 `#` 之前的片段後直接 `=== "/health"`。如此 `/a/../health` 會回 401 而非 403，語意更貼近 ADR-0004「只比對完全相等字串」。**目前實作已證實不可繞過，故不列為退回事由**；若 T-0016 有人動到這支檔案，順手改即可，不值得單開一張卡。
  3. **給 T-0018（部署卡）**：`infra/cloudrun-service.yaml` 的 startup／liveness probe 路徑必須是 `/health`（不可寫 `/health/`、`//health` 或任何帶點節段的變體——本卡實測這些一律 401，probe 會永遠失敗且極難查）。`monitor-health.yml` 打 `/health` 時不必帶任何憑證標頭；帶查詢字串亦可（實測 200），但依 WBS §1.5 仍建議不帶。
  4. **給 qa-cr（判準改良）**：`grep -nE "startsWith|RegExp|\*" src/plugins/basic-auth.ts` 這條判準中的 `\*` 會誤命中 JSDoc 的 ` * ` 續行（本卡開發者因此被迫全檔改用 `//` 註解）。建議 CR 時改用 `grep -nE "startsWith|endsWith|includes\(|RegExp|\.test\(|\.match\(" src/plugins/basic-auth.ts`，既精準又不干涉註解風格。此判準文字位於 WBS §1.5，屬我（dev-tl）自己的文件，將於 Gate 2 前的 WBS 例行維護一併修正，不在本卡範圍。
