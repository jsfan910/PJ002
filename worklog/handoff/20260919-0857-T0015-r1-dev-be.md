- 我做的假設與決策（含理由）：
  1. **`WWW-Authenticate` 標頭自行組出，不用 `@fastify/basic-auth` 的 `authenticate` 選項** —— 理由：該選項預設會附加 `, charset="UTF-8"`，與 ADR-0004 第 1 點、`04_API規格.yaml` `components.responses.Unauthorized.headers.WWW-Authenticate` 的範例值 `Basic realm="staging"` 逐字不符；改為在 `onRequest` hook 內於 `err` 存在時手動 `reply.header(...)`，同時涵蓋「外掛自身丟出的缺憑證/格式錯誤」與「本檔 `validate` 丟出的帳密不符」兩種錯誤來源，行為一致。
  2. **認證失敗一律經全域 error-handler 序列化，本檔不自行組裝 JSON 本文** —— 對應 dev-tl 於 T-0012 交接檔「下一步建議」第 1、2 點的交辦：不在自己的 register 子情境內再呼叫 `setErrorHandler`；帳密不符改為自行 `throw`（實際為 `done(new AppError(...))`，語意等價）而非依賴外掛原生錯誤訊息。缺憑證／格式錯誤時外掛會丟出它自己的 `FST_BASIC_AUTH_MISSING_OR_BAD_AUTHORIZATION_HEADER`（`statusCode: 401`，訊息為固定字面值 `"Missing or bad formatted authorization header"`，不含任何內部細節），流向 error-handler 的非 `AppError` fallback 分支（`resolveCode(401)` → `E_UNAUTHORIZED`），驗證後判定此訊息可接受（不洩漏內部資訊），不需額外包一層 `AppError`。
  3. **`registerBasicAuth`／`registerStatic` 皆為直接呼叫的一般函式，不透過 `app.register()` 建立巢狀子情境**（僅 `@fastify/basic-auth`／`@fastify/static` 兩個外掛本身透過 `app.register()` 註冊，因其套件內部已用 `fastify-plugin` 打破封裝，效果等同掛在根實例）——與 WI-02 `registerErrorHandler` 的作法一致，理由相同：避免 Fastify 封裝邊界讓之後才註冊的手足外掛（static／routes）繼承不到 hook。
  4. **`/health` 豁免用 `new URL(rawUrl, "http://localhost").pathname` 取 pathname**，不用字串切割（如 `split("?")[0]`）——理由：`URL` 的 pathname 解析同時處理查詢字串與 hash 且是標準 API，比手動字串處理更不易寫錯；已用 `/health?cb=1`（查詢字串）與 `/health/`（尾斜線，驗證不會被誤判為相等）兩個測試驗證行為正確。
  5. **靜態託管明確關閉快取**（`cacheControl:false`、`etag:false`、`lastModified:false` ＋ `Cache-Control: no-store, private`）——WBS §1.5 本身沒有這條指令層級的驗收，但任務卡背景欄「不得快取洩漏憑證」與 SD §6.2「未帶憑證取 `public/` 資產同樣回 401」的精神一致：避免受保護內容被中介快取後，之後的請求（含未帶憑證者，若快取層本身設定不當）拿到快取本文而繞過認證。此為保守的防禦性設計，非規格明文要求的單一判準，故列於此供 dev-tl 復核是否過度設計。
  6. **`src/plugins/basic-auth.ts` 全檔改用 `//` 行註解，不用 `/** */` 區塊註解** —— 理由：WBS §1.5 驗收指令 `grep -nE "startsWith|RegExp|\*" src/plugins/basic-auth.ts` 要求無輸出，而專案慣用的 JSDoc 區塊註解每行以 ` * ` 開頭會被同一個 grep 判準誤判為違反「禁止萬用字元」；改用 `//` 行註解可在保留完整說明的同時通過此判準的字面檢查。`src/plugins/static.ts` 不受此判準限制，維持專案慣用的 JSDoc 風格。
