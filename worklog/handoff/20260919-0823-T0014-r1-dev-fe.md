- 我做的假設與決策（含理由）：
  1. **不在 `index.html` 加入任何 `<script>` 標籤**：因為 `todo-view.js`／`todo-store.js` 尚不存在，加入會造成 404（雖不影響版面渲染），且會涉入「進入點該長什麼樣子」這個屬於 T-0017 單向資料流設計的決定；依「不擴大範圍」原則，本卡只建立骨架，接腳本的動作留給下一張卡或 Leader 裁決（見下）。
  2. **`api-client.js` 的 `ApiError`／`NetworkError` 為兩個獨立的具名例外類別**，而非單一例外＋錯誤碼：因為網路層失敗（斷線）與伺服器已回應但為錯誤狀態碼是兩種不同的使用者提示情境（AC-008-3 需要「連不上伺服器」與「伺服器回報驗證失敗」分開處理的彈性），且 WBS §1.4 要求「解析統一錯誤物件並轉為具名例外」，用兩個類別更符合「具名」的字面要求。
  3. **`listTodos()` 不帶參數時不送出 `status` 查詢字串**（而非明確送 `status=all`）：因為 `04_API規格.yaml` 的 `StatusFilter` 本身 `default: all`，省略參數與明確送 `all` 對後端是等價的，省略較符合「篩選不寫入網址、不持久化」（BR-010）的精神——api-client 不替呼叫端加上它沒有明確要求的狀態。
  4. **`public/assets/api-client.js` 對 `DELETE` 的 204 回應直接回傳 `undefined`，完全不呼叫 `response.json()`**：因為 `04_API規格.yaml` 明定 204 無回應本文，呼叫 `.json()` 在多數 `fetch` 實作上會因空本文而拋例外；以 `response.status === 204` 提前 return 是最直接且不依賴實作細節的做法。
  5. **`.add-form__input` 由 `flex: 1 1 240px` 改為 `flex: 1 1 auto; min-width: 240px; height: var(--min-tap)`**：原寫法在 `flex-direction` 隨斷點由 `row` 變 `column` 時，`240px` 的 flex-basis 從「寬度基準」變成「高度基準」，造成手機尺寸下輸入框變成 240px 高的方塊（違反排版意圖，雖未直接違反任何一條 acceptance 逐字要求，但明顯是缺陷）。改用不隨主軸方向變化語意的 `min-width` ＋ 固定 `height`，兩種尺寸皆實測 44px 高。
  6. **未使用 `npx http-server` 透過 `.claude/launch.json` 預覽**：因為 `preview_start` 的 `launch.json` 綁定在根目錄（`C:\Users\excal\Projects\Claude\soft-dev-team-260919\.claude\launch.json`），而規則要求根目錄永遠停在 main、不可寫入非本卡 outputs 的檔案；改用暫存目錄下的一支最小 Node 靜態伺服器腳本（非專案檔案，不進版控）搭配瀏覽器 `navigate` 直接測試兩種尺寸，驗畢已終止程序並確認埠號釋放（見下方驗證輸出）。
