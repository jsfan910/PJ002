### 阻擋級退回項（具體要改哪裡）

**R-1：流量驗證用的是代理指標，不是 acceptance 指定的 `status.traffic`；且「100%」從未被檢查。**

- 位置：`.github/workflows/deploy-staging.yml` 的 `verify_traffic()`（約 227–233 行）與 `ensure_traffic_on_latest()`（235–248 行）；`scripts/deploy-staging.sh` 127–144 行；連帶 06 §6.10.3「關鍵發現」段、§6.10.4「修法」段、§變更紀錄 T-0045 列、README「本機等效指令」`scripts/deploy-staging.sh` 那一條。
- 事實：判定式是 `latestReadyRevisionName == latestCreatedRevisionName`。`status.traffic` 從頭到尾不參與判定，只在失敗訊息裡印出。acceptance 第 2 條要求的是「讀 `status.traffic`，若新 revision 未拿到 **100%** 流量則…」以及「確認 `latestReadyRevisionName == **接流量的 revision**」——「接流量的 revision」只能從 `status.traffic` 取得，實作把它替換成 `latestCreatedRevisionName`，「接流量」這層語義整個消失。
- 為什麼不能放行（三點，任一點都足夠）：
  1. **百分比不檢查＝有實際漏判**。`rollback-staging.sh` 允許把流量釘到任意 revision，未來若做 canary／分流（例如 `--to-revisions LATEST=50,<old>=50`），`latestReadyRevisionName` 仍會等於新 revision，判準通過，但新 revision 只有 50% 流量，acceptance 要的 100% 沒達到，D-018「驗證失效」以另一種形式留著。
  2. **判準依賴未文件化的平台行為**。本次實查已證明：00004～00018 全部 `Ready=True`，而釘死期間 `latestReadyRevisionName` 卻停在 `00003-lt2`——這與 Knative 對該欄位的公開語義（「最新一個 Ready 條件為 True 的 revision」）相反。dev-ops 的觀察屬實，但那是 Cloud Run 目前實作的副作用，不是規格。角色定義的安全邊界判準同型原則：**第三方平台行為不是規格，換一個平台版本或部署形態就沒了**。本卡的全部價值就是「讓 pipeline 真的偵測得到流量沒切」，判準底座不能是觀察。
  3. **修正成本極低，沒有不做的理由**。資料本來就在手上，`csv[no-heading]` 格式已於驗證 5 實測可解析。
- 具體改法（兩處同步，維持既有 `ensure_traffic_on_latest` 的重試結構不變）：
  1. 把 `get_traffic_table()` 的格式由 `table[no-heading]` 改為 `csv[no-heading](status.traffic.revisionName,status.traffic.percent)`（`table` 格式輸出 `['todo-app-00018-xq4']  [100]`，帶方括號與引號，無法解析）。
  2. `verify_traffic()` 改為直接從 `status.traffic` 求該 revision 的流量百分比並要求等於 100，例如：
     ```bash
     verify_traffic() {
       local expected_revision="$1" table pct latest_ready
       table="$(get_traffic_table)"                    # csv: revisionName,percent
       pct="$(echo "${table}" | awk -F, -v r="${expected_revision}" '$1==r {s+=$2} END {print s+0}')"
       latest_ready="$(get_latest_ready_revision)"
       echo "status.traffic=$(echo "${table}" | tr '\n' ';')；${expected_revision} 取得 ${pct}%；latestReadyRevisionName=${latest_ready}"
       [ "${pct}" = "100" ] && [ "${latest_ready}" = "${expected_revision}" ]
     }
     ```
     即：**主判準為 `status.traffic` 中該 revision 拿到 100%**，`latestReadyRevisionName` 比對降為併行的輔助條件（正好對應 acceptance 「同時確認」的字面要求）。
  3. STEP_SUMMARY 的「流量」欄改為填入實際讀到的 `pct`，不要寫死 `100%`（現行成功分支是硬寫 `| 100% |`，等於把未經證實的值寫進報告）。
  4. 06 §6.10.3「關鍵發現」段與 §6.10.4「修法」段、§變更紀錄 T-0045 列、README 該條敘述同步改寫：把 `latestReadyRevisionName` 的角色從「**可靠依據**」降為「輔助佐證（Cloud Run 實測觀察，非文件化保證）」，主判準明寫 `status.traffic` 的百分比。06 是 frozen 規格文件，後人會照著引用，措辭必須精確。
