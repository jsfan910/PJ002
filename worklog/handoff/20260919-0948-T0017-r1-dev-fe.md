### 我做的假設與決策（含理由）

1. **未修改 `public/styles.css`，即使派工提示詞提到「styles.css 若需微調」**。任務卡 `outputs` 明確只列 `todo-store.js`／`todo-view.js`／`todo-store.test.mjs`／`index.html`（僅一行），且任務卡 acceptance 2 明文「不改本卡 outputs 以外的檔案（git diff --stat 佐證）」，角色協定（`.claude/agents/dev-fe.md`）亦禁止改 outputs 以外的檔案。派工提示詞的「若需微調」是條件句，我判斷「不需要」：改以動態元素的行內 `style` 屬性（可讀取既有 `:root` CSS 變數如 `var(--color-border)`）達成所有版面需求（44×44 點擊區、不橫向捲動、完成刪除線樣式），因此完全不用碰 `styles.css`。這同時解掉任務卡與提示詞的潛在衝突，若 Leader 認為應該直接編輯 `styles.css`，屬於範圍變更，請另行裁決（見下方「需要 Leader 裁決的事」）。
2. **`todo-view.js` 同時擔任「controller」角色**（事件綁定＋重繪）。任務卡 outputs 沒有獨立的 controller 檔案，且派工提示詞明寫「public/assets/todo-view.js（render 與事件綁定，依 state 重繪）」，SD §3.2 的資料流箭頭圖也只畫到 `todo-view`，未另開模組；因此把「使用者事件 → action 呼叫」與「訂閱重繪」都放在同一檔，並在檔頭註解明確標示兩個職責的分界（事件綁定區塊 vs. render 函式群）。
3. **關閉新增輸入框的原生 `required` 屬性**（`addInput.required = false`，只在 JS 執行時的 DOM 屬性層級關閉，未改動 `index.html` 原始檔）。原因：`required` 會讓瀏覽器對「完全空字串」的送出顯示原生提示，繞過我方 `error-message` 區塊，與 AC-001-2「畫面上顯示可讀的錯誤訊息」的預期呈現位置不一致；全空白字元（`"   "`）本來就不受 `required` 擋（HTML5 規則），所以這條調整只補齊「完全空字串」這一種情況，讓兩種空標題情境都統一走同一個錯誤顯示路徑。
4. **`setCompleted`／`add`／`updateTitle`／`remove` 失敗時不自動重新載入清單**，只設定 `error` 讓使用者看到訊息；重新載入交給「重試」按鈕或使用者下一個操作（如切換篩選）自然觸發。理由：若在顯示 `E_NOT_FOUND` 等訊息的同一個 tick 自動 `load()`，`load()` 會立刻把 `error` 清成 `null`（因為 `load` 一開始就 `setState({error:null})`），訊息會瞬間被蓋掉，使用者看不到；保留「顯示訊息＋手動重試」比「靜默自動刷新」更符合 AC-008-3「顯示可讀的錯誤訊息」的字面要求。
5. **編輯／新增表單一律先做本地 `trim()` 後長度 1~200 驗證，通過才呼叫 API**；驗證失敗時完全不送出 HTTP 請求。這與 T-0016 交接檔的建議一致（避免「trim 後剛好 200 但原始字串 >200」被 schema 層擋成 400 的邊界），也降低不必要的伺服器往返。
6. **`renderError` 每次都重新建立「重試」按鈕元素**（而非快取重用），因為 `errorMessageEl.textContent = error.message` 會清空既有子節點；影響僅為多一次 DOM 建立，效能上可忽略（列表項目才是效能考量重點，已用 `DocumentFragment`）。
7. **本機驗證環境**：`.env` 由 `.env.example` 複製產生（Leader 裁決 D-01 的本機佔位值 `dev`/`dev`），已列入 `.gitignore`，未進版控（`git status --short` 佐證）；驗證完成後已 `docker compose down -v` 清空容器、volume、network，且以 `curl` 確認 8080 埠已釋放。
