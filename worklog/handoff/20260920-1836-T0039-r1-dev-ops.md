- 我做的假設與決策（含理由）：
  1. **合併四個獨立 step 為一個 bash 步驟**：GitHub Actions 的 step 之間無法乾淨表達「失敗後跳回上一步重跑」，唯一乾淨做法是把 deploy＋兩種 verify 封裝成 bash 函式放在同一個 step 內用程式邏輯控制重試；因此拿掉原本 `verify（取服務網址）`／`verify（輪詢 /health 至 200）`／`verify（帶憑證呼叫 /api/v1/todos 確認 200）` 三個獨立 step 名稱，改用單一 step `gcloud run deploy ＋ verify（含一次自動重試）`。行為（輪詢至 200、帶憑證呼叫、STAGING_BASE_URL 比對警告）完全保留，只是不再是獨立可見的 step 名稱。已用 actionlint／yaml-lint 驗證語法正確。
  2. **健康檢查（不帶憑證）失敗不觸發本建議的自動重試**：06 §6.7 建議二的情境是「verify（帶憑證）」的一次性解析異常，若 `/health` 本身輪詢 5 分鐘都不過，通常代表部署本身有問題（非 secret 解析的一次性異常），維持原本「直接判紅」行為，避免掩蓋真正的部署缺陷。
  3. **repository variables 命名**：`SECRET_VERSION_DATABASE_URL`／`SECRET_VERSION_BASIC_AUTH_USER`／`SECRET_VERSION_BASIC_AUTH_PASS`，與 secret 名稱（`database-url`／`basic-auth-user`／`basic-auth-pass`）對應但轉大寫底線，與現有 `GCP_PROJECT_ID` 等變數命名風格一致；預設留空即走「自動取最新 ENABLED 版本」路徑。
  4. **§7 參數表與變更紀錄表本卡不動**：任務卡 outputs 明寫「僅新增 §6.9 實作紀錄；§1～§6.8 文字不動，規格文字調整由 T-0040 plan-sd 負責」，§7 與變更紀錄表雖與本卡改動相關，但屬「規格文字」範疇，已在 §6.9 內明確列出待同步項，留給 T-0040。
  5. **本機 `gcloud secrets versions list` 唯讀驗證**：CLAUDE.md 鐵則禁止 agent 讀取／索取／代填憑證值，但未禁止唯讀查詢版本號與狀態（`versions list`，不含 `versions access`）；本機環境已是使用者自行登入的既有 session（`excalibur.star@gmail.com`），非我索取或代填，用於驗證 `resolve_version()` 邏輯是否正確解析出「跳過已停用版本、取最新 ENABLED」這點行為，判斷此查詢在規則許可範圍內且是驗收條件明確要求的項目。
