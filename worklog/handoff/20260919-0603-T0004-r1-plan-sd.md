- 我做的假設與決策（含理由）：
  - **多寫一份 ADR-0004（認證與同源部署）**。理由：Q-008（擋整站）、O-005（`/health` 豁免）、O-004（同源）三者單看都簡單，湊在一起會互相破壞 —— 不豁免則 NFR-003 永遠不通過，跨來源則 CORS 預檢（不帶 `Authorization`）會被 Basic Auth 擋成 401 使前端完全不能用。把三者的取捨拆散寫在三處，讀的人不會發現它們有交互作用。提示詞已授權「若有取捨可加 ADR-0004」。
  - **選 Fastify 而非訓練資料更多的 Express**。理由：三項最容易出錯的硬約束（Basic Auth 路徑豁免、結構化日誌五欄位、統一錯誤物件）在 Fastify 都是官方外掛或內建能力，Express 則三項都要手工黏合，而黏合處正是 Sonnet 等級開發者最容易出錯的地方。代價（訓練資料較少）已在 ADR-0001「後果」明確承擔，並要求開發卡的「背景與限制」欄必須附上官方外掛名稱與版本。
  - **選 Render ＋ Neon 而非 Cloud Run／Fly.io**。理由：後兩者**建立帳號即需綁信用卡**，與 Epic「憑證與雲端帳號由使用者提供」的體驗摩擦最大；且 Render 的 Docker runtime 讓本機 `docker build` 成功幾乎等同雲端建置成功，是「可離線驗證」限制最直接的滿足方式。
  - **不使用 ORM**。理由：2 張表、6 個查詢，Prisma 的 `generate` 步驟與平台專屬引擎二進位檔是免費方案部署最常見的卡關點。代價（SQL injection 風險回到人）以「禁止任何字串拼接 ＋ CR 以 repository 層有無 `${` 為單一判準」控制，已寫入 SD 第 6.3 節與 ADR-0002。
  - **`PATCH /api/v1/todos/{id}` 一個端點同時服務 UC-003 與 UC-005**，body 兩欄皆選填但至少要有一個。理由：兩者都是「部分更新同一個資源」，拆成兩個端點會讓端點數與前端 client 方法都翻倍，與「規模刻意小」相違；`isCompleted` 採**設定目標狀態**（O-002 裁決）因此冪等，前端失敗重試可無腦重送。
  - **採用 `/api/v1` 版本前綴**。理由：Epic 明載「後端要有 API，將來可能接手機 App」，版本前綴現在零成本，日後可免去一次破壞性改名。已列入 SD 第 9 章 SD-05 供審核者表態；若判定為擴大範圍，移除是單點變更（兩處）。
  - **排序 tie-break 收斂為 `ORDER BY created_at DESC, id DESC`**。理由：這是我在審核 T-0003 時記下的瑕疵。NFR-007 的 500 筆若以腳本批次建立極易同秒碰撞，無 tie-break 則測試斷言不穩定。加 `id` 作次要鍵後順序為決定性。
  - **AC-009-5 改以「規範意圖」驗證，判準寫死為兩條**（無 `Access-Control-Allow-Origin: *` ＋ 無跨來源預檢）。理由：該 AC 的 Given 前提「前端與 API 部署於不同來源」在 O-004 同源裁決下不成立，但其規範意圖（不得用萬用字元 CORS）仍必須被驗。判準已同步寫入 traceability 的「特殊驗證方式的 AC」表。
  - **`E_EMAIL_TAKEN` 採 409 而非 400**。理由：重複 Email 是資源衝突而非輸入格式錯誤，409 語意最準；AC-009-3 的列舉未含 409 但該 AC 的實質要求是「語意正確」。屬 P1，Gate 1 不受影響；已列入 SD 第 9 章 SD-03，若測試團隊要求嚴格限縮於列舉值，改為 400 是單點變更。
  - **`/health` 不查資料庫**。理由：它回答的是「這個程序活著且能回應 HTTP」。若查資料庫，Neon 的短暫抖動會讓 Render 判定實例死亡而重啟，反而降低 NFR-003 的可用性；且回應內容越豐富，這個對全網公開的路徑洩漏面越大。
  - **`002` migration 的第一行為 `TRUNCATE TABLE todos;`**，與 `owner_id SET NOT NULL` 同一個檔。理由：BR-032／Q-011 裁決「導入 P1 時直接清空」，但 SA 未指定由誰在哪一步執行。放進同一個 migration 使其**不可能被遺漏**（分開執行的話，既有無主資料會讓 `ALTER` 失敗或留下違反 BR-023 的孤兒列）。
  - **`users.email` 用 `citext` 而非 `varchar`**。理由：`Alice@example.com` 與 `alice@example.com` 必須視為同一帳號，否則 BR-024 的唯一性可被大小寫繞過。SA 只說「全系統唯一」，未指定大小寫敏感度，此為保守補強。
