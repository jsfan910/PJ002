## 重要操作紀事（誠實揭露，影響部分中間結果的判讀）

1. **暖身結果**：兩次 `/health` 皆 200，耗時 0.05s 內，staging 當時已是熱機狀態（T-0027 剛部署驗證過），未觀察到 1–3 秒冷啟。
2. **e2e 修正**：對 staging 導覽時，Chromium／Edge 用 HTTP/2／QUIC 在本執行環境會 `net::ERR_ABORTED` 逾時（`curl`／`node fetch` 對同網址皆正常 200，只有瀏覽器網路層卡住）；用最小重現腳本排除後，在 `tests/e2e/playwright.config.ts` 的 `use.launchOptions.args` 加 `--disable-http2`、`--disable-quic` 修復（`page.goto` 只需前者，`page.reload()` 需兩者都加，已各驗證 3 次穩定重現／修復）。對本機 docker compose（HTTP/1.1）無影響。
3. **本卡自身操作疏失（誠實記錄）**：加上第 2 點修正後，啟動了新的背景 e2e 執行，但**忘記先停止前一個仍在背景執行的舊版本 e2e 程序**，導致兩組測試同時對同一個 staging 服務跑 `apiClearAll()`／`apiCreate()`，互相競態造成一批「筆數不符」的假性失敗（例如 `Expected: 3 Received: 4`）。發現後已用 `TaskStop` 終止舊程序，**本報告採用之後單獨、乾淨執行的最終結果**，不採計併發污染期間的失敗。
4. **test:integration:qa 的 `TC-014` 會清空 staging 全部既有資料**（`list.json().map(todo => deleteTodo(todo.id))`，BR-028 驗證的必要手段）。這對共用 staging 的其他測試角色（如 qa-uat T-0029）與本卡自己想保留的 TC-080 基準資料都是破壞性的；本輪因此無法取得「同一批資料」跨越一次真實部署前後的乾淨對照（見下方 TC-080）。**建議下一輪**：若要對 staging 做 TC-080 的直接量測，`test:integration:qa`／`test:e2e` 應與該量測分開時段執行，避免互相清空。

## 環境差異說明（與 r2 本機基準對照）

- **TC-079**：本機無 TLS 終止層，r2 記「阻擋」；staging 實測為 302（非預期的 301），列為失敗＋規格覆核建議，見上表。
- **e2e HTTP/2／QUIC**：本機 docker compose 為 HTTP/1.1，不受影響；staging（Cloud Run／Google Frontend）走 HTTP/2，本執行環境的瀏覽器網路層與之互動需要 `--disable-http2 --disable-quic` 才能穩定導覽／`reload()`，已寫入 `tests/e2e/playwright.config.ts` 並附註說明；此為**環境差異的最小修正**，不影響測試斷言本身。
- **e2e 部分 TC 間歇性失敗（TC-067、TC-009）**：本機 r1/r2 從未出現，只在對 staging 執行時出現，機率約 2~4 成（多次重跑樣本）。**已排除本卡的並行污染疏失**（見上「操作疏失」第 3 點）後仍會再現，故懷疑是前端顯示錯誤訊息的邏輯在真實網路延遲下有時序競態；非本卡環境修正範圍，列為缺陷候選，見下。
- **perf 數字量級**：staging 有真實網路往返（TCP／TLS／跨區），數字必然高於本機 loopback；GET P95 staging 156.4ms vs 本機 47.7ms、POST/PATCH/DELETE P95 約 300ms/159ms/317ms vs 本機個位數~十位數 ms，量級差距符合預期（跨區網路延遲），且皆遠低於門檻，PASS 判定不受影響。

## 觀察與缺陷候選（交 qa-lead 編號與裁決）

1. **TC-079 規格與平台行為不一致**：Cloud Run／Google Frontend 對 HTTP 請求回 302 而非 301。屬規格/ADR 認知落差，非應用程式碼缺陷（團隊對此無程式碼可改）。建議：修訂 `20_測試案例.md` TC-079 判準與 `06_部署架構與CICD.md` 相應敘述為「回 3xx（301 或 302 皆視為合規）且 `Location` 為 HTTPS」。
2. **e2e TC-067／TC-009 間歇性失敗**（前端「顯示可讀錯誤訊息」在 staging 真實網路延遲下有時序性失敗，`error-message` 保持 `hidden`）：多次重跑証實非本卡環境修正造成、非資料污染造成（皆已在乾淨、單獨執行下再現）。建議 qa-lead 開缺陷單（初評 S3：有繞過，重試通常會過；影響 BR-029／BR-030 錯誤顯示的可靠性），指派 dev-fe 檢視前端錯誤狀態更新的時序邏輯是否有 race condition。原始失敗紀錄見下方節錄。
