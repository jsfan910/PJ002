## 3. 需要你裁決的項目

### ① Gate 2 判定本身

1. **核心爭議**：第 1 項 P0 通過率 96.19% 未達 100%，但缺口 4 條沒有一條是產品做錯，且每一條的處置都已裁決在 Gate 2 之後。現在判「有條件通過」給出明確答覆，還是照字面判「不通過」再多跑一個循環。
2. **證據觀點**：07 §4 明文「第 1～7 項為擋關項，任一不達標即不可發布」；同時 105 條中不通過 0、阻擋 0，NFR-003 滿分，其餘六項擋關項全部達標，回滾與零停機部署皆實測。
3. **選項**：

   | 選項 | 做法 | 代價 |
   |---|---|---|
   | A. 有條件通過（建議） | 判通過，條件三項：TC-080 定案（② ）、發布前輪換 staging 帳密、D-017／Firefox／cron 修文列 Gate 2 後待辦追蹤 | 07 §4 的字面門檻被繞過一次；日後只讀規格的人會覺得判準失效（已列框架待辦修判準） |
   | B. 不通過（字面） | 依 07 §4 字面判不可發布，等 D-017 修好、Firefox 於非沙盒補跑、TC-080 補做後出 Gate 2 r3 | 至少再一個工作循環（dev-fe 修正＋重測＋非沙盒環境），而這三件事你已同意不緊急；「不通過」會被誤讀為做壞了 |
   | C. 先不判 | 維持 r1 的「阻擋，待補驗」直到 B 的三件事完成 | 同 B 的等待，且缺一個明確答覆 |

4. **建議 A**。理由：A 是唯一不用新增工作、也不用當場改判準就能給出明確答覆的做法，且缺口 4 條各自已有處置與繞過。
5. **推翻成本**：低。選 A 後想改 B，測試總結 r3 的 11 項數字全部沿用，只需在 D-017 修好與 Firefox 補跑後重算第 1 項，不必重跑 NFR-003（24 小時證據已固定）。選 B 後改 A 只是重寫一份 Gate 報告。

### ② TC-080（部署後既有資料仍存在）如何定案

1. **核心爭議**：TC-080 對應 S1 情境「重新部署後資料消失」，目前只有三項間接證據（部署期間 /health 零中斷、Neon 與 Cloud Run 運算分離、回滾只切 revision 不動資料層），沒有「同一批資料跨越一次部署前後」的直接比對。補做需要 staging 憑證，agent 不索取、不代填，只有你能做。
2. **證據觀點**：07 §4「沒有證據的通過不算通過」，而 TC-080 寫定的證據形式就是前後比對；另一方面三項間接證據互相獨立且都成立，本機等效 TC-093 通過。
3. **選項**：

   | 選項 | 做法 | 代價 |
   |---|---|---|
   | A. 你親自補做（建議） | 約 15 分鐘：以 staging 帳密透過 API 建 3 筆帶固定前綴的待辦 → 用 `gcloud run services update todo-app --region asia-east1 --update-env-vars DEPLOY_PROBE_GATE2=<時間戳>` 觸發新 revision → 再列一次待辦比對筆數與內容。期間不要跑 `test:integration:qa`。把輸出貼給我，我更新 TC-080 為通過（第 1 項升為 102／105） | 你的 15 分鐘；期間 staging 獨占 |
   | B. 追認間接證據 | Leader 明文把 TC-080 改判通過，寫進 Epic、測試案例與追溯矩陣 | 一條 S1 情境的 TC 不是用它寫定的方式驗的 |
   | C. 維持部分通過 | 列殘留風險，不補做 | 第 1 項永遠到不了 100%；裁決紀錄與文件的矛盾持續 |

4. **建議 A，若你不想花這 15 分鐘就選 B**。理由：這是唯一「一次操作就能從間接變直接」的缺口，而它對應資料遺失這種 S1 情境。
5. **推翻成本**：極低。A 與 B 之間隨時可換，只改第 1 項數字（101 ↔ 102）。

### ③ Gate 2 通過後的下一步

1. **核心爭議**：E-001 是框架試跑。Gate 2 之後是開 P1（多使用者帳號，US-011～013，規格與 18 條 TC 已凍結），先清 Gate 2 後待辦，還是就此結案改用框架 v1.1 起下一個 Epic。

   | 選項 | 做法 | 代價 |
