### 3.1 TC-037：判**測試前置步驟競態（flaky test），非產品缺陷**；TC-037 維持通過

#### (1) 事實（兩次失敗、24 次執行）

#### (2) 根因（本卡讀碼獨立判定，非採信轉述）

`tests/e2e/us004-delete.e2e.test.ts` 第 62 ~ 74 行（**程式碼為原文；行末 `//` 後的中文說明是本卡加註，原檔只有第 67 行的「背景已被刪除」一則**。未加註的原文見 §7.3）：

```ts
test("TC-037：刪除已被刪除的待辦不產生系統錯誤畫面", async ({ page }) => {
  const todo = await apiCreate("TC-037：待刪除");   // node 端直打 POST，建立成功
  await page.goto("/");                             // 只等 load 事件，不等清單 API 回應

  const item = page.getByTestId("todo-item").filter({ hasText: "TC-037：待刪除" });
  await apiDelete(todo.id);                         // node 端直打 DELETE（背景刪除）

  page.once("dialog", (dialog) => dialog.accept());
  await item.getByTestId("todo-item-delete").click();   // 自動等待該元素，上限 30 秒
  await expect(page.getByTestId("error-message")).toBeVisible();
  await expect(page.locator("body")).not.toBeEmpty();
});
```

三項事實決定了這是一個競態：

1. **`page.goto("/")` 預設 `waitUntil: "load"`**，只保證 HTML 與 `<script type="module" src="/assets/todo-view.js">`（`public/index.html:87`）已執行完畢，**不保證前端發出的 `GET /api/v1/todos` 已經回來**。模組腳本在 `load` 之前執行，所以那個請求**已經送出但可能仍在飛行中**。
2. **`apiDelete` 是 node 端直打 HTTP**（`tests/e2e/lib/api-helper.ts`），與瀏覽器是兩條獨立連線，**先後到達伺服器的順序不受測試控制**。
3. 若伺服器先處理 `DELETE`、後處理瀏覽器的 `GET`，**回應的清單不含該筆 → 項目從未渲染**。而前端**沒有任何重新載入的機會**（見下一小節），因此 `click` 必然等滿 30 秒逾時。

**同一檔案內的對照組即是反證**：TC-034（第 21 ~ 22 行）在 `page.goto("/")` 之後有一行 `await expect(page.getByTestId("todo-item")).toHaveCount(3);`，明確等到清單渲染完成才進行後續操作；**TC-037 缺這一步**。TC-035／TC-036 沒有背景刪除，`click` 的自動等待自然會等到項目出現，因此不受影響。

#### (3) 正面否證：**T-0038 的 `stale` 行為不可能是原因**

這是 r4 §6 裁決事項 B 最擔心的情境（前端狀態時序重寫可能在別的路徑引入迴歸），必須正面回答，不能只說「看起來無關」。

`public/assets/todo-store.js` 的 stale 機制語義為：**只有經過 store 的動作才會 `beginOp()` 佔號**（`load`／`add`／`updateTitle`／`setCompleted`／`remove`，以及 `add`／`updateTitle` 的同步驗證失敗分支）。`isStale(token)` 為真的**必要條件**是「本動作開始之後，又有另一個動作 `beginOp()`」。

在 TC-037 的時間窗內：

- **store 內只發生一個動作**。`public/assets/todo-view.js` 第 302 ~ 304 行的啟動序列是 `todoStore.subscribe(render); render(); todoStore.actions.load();` —— **`actions.load()` 只被呼叫一次**；本卡以 `grep -n "actions.load\|setInterval\|setTimeout" public/assets/todo-view.js` 確認**全檔沒有任何輪詢或計時器**（輸出見 §7.3），其餘 store 動作全部綁在使用者事件上（`submit`、`click`、`change`）。
- **`apiDelete` 不經 store**，不呼叫 `beginOp()`，`opSeq` 不會遞增。
- TC-037 在失敗的那個 `click` 之前**沒有任何使用者事件**。

因此 `isStale(token)` 在該時間窗內**恆為 false**，`{ok: true, stale: true}` 這條分支**不可能被執行**。**T-0038 的行為改變與本失敗無關。**

**順帶排除的另兩個候選**：①瀏覽器快取 —— Playwright 每個 test 使用獨立 context，無跨 test 快取；且 `src/plugins/static.ts` 對靜態資產設 `Cache-Control: no-store, private`。②後端讀寫不一致 —— 失敗只在慢輪出現、快輪 22 次全過，且同一 `DELETE` 的語意在 TC-030 ~ TC-036 全部通過。

  - **與 D-017 的分界**（避免雙重標準）：D-017 的失敗是**斷言本身不成立**（`error-message` 應可見而為 `hidden`），根因在產品碼，故判「部分通過」＋立 S3 缺陷；本筆的失敗是**斷言未被執行**，根因在測試碼。兩者分屬不同類別。
