依 Leader 指示的方法重現：先導覽帶帳密網址一次建立認證快取，再導覽裸網址操作 —— 頁面正常載入，`GET /api/v1/todos?status=all` 回 200，清單正常渲染，且本輪完成 US-001～US-010 全部十則的實際操作與驗證。r3 的阻擋是**工具操作問題**（未執行「先帶帳密、再裸網址」兩步驟中的第二步；其截圖目錄 `uat-screenshots/r3/README.md` 內容亦只是文字敘述、非實際擷取畫面），非環境或程式碼缺陷，與 Leader 派工時的實測一致。

**本輪新發現且需記錄的環境現象**：staging 資料在測試期間被**持續快速刪除／清空**（同一筆剛以 `POST` 建立、幾百毫秒到數秒內以 `GET`／`PATCH`／`DELETE` 存取即回 404），推測是其他 QA agent（qa-at 系列）同時對同一 staging 做自動化 E2E／清理測試所致。此現象讓多次 UI 操作（編輯、切換、刪除）在點擊與送出之間，資料已被別的 agent 刪除，導致看到「找不到這筆待辦，可能已被刪除」的畫面 —— **這件事本身反而正確驗證了 AC-003-5／AC-004-4 的錯誤處理**，但也代表：多個 QA agent 不應同時對同一份可變的 staging 資料做寫入型測試，否則彼此結果會互相干擾、難以歸因。建議記入「需要 Leader 裁決的事」。

- `document.querySelector('input[placeholder]').maxLength` 執行結果為 `200`；實際能輸入的字元數上限即為 200，第 201 個字元無法被打入（HTML `maxlength` 屬性擋下，比「送出後顯示錯誤」更早一步阻止）

## 冷啟動耗時記錄

**方法說明**：受限於單次工具呼叫時間與任務排程，未執行「閒置 15 分鐘後首次載入」的等待（Leader 派工當下 staging 已被多個 agent 持續存取，難以自然達到 15 分鐘閒置）。**記錄為「未量測」（真冷啟動）**，改以本輪實際觀測到的首次／後續載入耗時供 NFR-001 離群值參考：

- 本輪第一次以帶帳密網址導覽並完成登入快取建立後，再導覽裸網址：頁面於瀏覽器內立即渲染出清單（無明顯延遲，主觀 <1 秒）
- 之後同一分頁多次重新導覽裸網址，`performance.getEntriesByType('navigation')` 讀出的 `loadEventEnd` 約 104～136 毫秒（此為**服務已熱機**狀態下的數字，非冷啟動代表值，Cloud Run `min-instances=0` 的真實冷啟動依 ADR-0005 預期為 1–3 秒量級）
- 結論：本輪未取得真正的冷啟動（15 分鐘閒置後）耗時；如需 Gate 2 前完整量測，建議另排一個時段讓 staging 閒置 15 分鐘以上再單獨量測，且該時段內其他 qa agent 暫停對 staging 的存取

## 環境現象：staging 資料在測試期間被快速刪除（非本輪程式碼缺陷，但需 Leader 知悉）

**觀察**：多次以 curl 或 UI 建立一筆待辦後，在 0.1～3 秒內以 `GET`／`PATCH`／`DELETE` 存取同一 id，經常已回 `404 E_NOT_FOUND`；同時清單內容（其他 agent 建立的 `TC-0xx` 命名項目）在每次重新整理間也持續變動、數量增減。

**佐證**（節錄自本輪 Bash 執行紀錄）：
```
POST /api/v1/todos {"title":"UAT-R2-curl-3"} → 201
GET /{id}（第1次，間隔約0秒）  → 200
GET /{id}（第2次，間隔約1秒）  → 200
GET /{id}（第3次，間隔約2秒）  → 200
GET /{id}（第4次，間隔約3秒）  → 404
GET /{id}（第5次，間隔約4秒）  → 404
```

**判斷**：非本應用程式碼缺陷（NFR-006 資料持久性驗證的是「重啟／重新部署後」資料是否還在，不是「其他測試同時刪除」）；最可能原因是同時在跑的其他 QA agent（qa-at-T0021、qa-at-T0021-r2、qa-at-T0028 等，見本輪任務環境的 agent 名單）對同一 staging 執行自動化 E2E 測試，其測試前置或收尾動作可能包含「清空 / 刪除全部待辦」之類的固定資料重置步驟，殃及其他 agent（含本輪）建立的資料。

**影響**：本輪多筆 UI 操作因此改採「以 curl 在單一指令內緊接完成建立與驗證」取得乾淨證據；受影響但仍取得等價證據的項目已在對應章節註明。P0 十則的通過判定不受影響（每條 AC 皆有至少一組乾淨證據）。

**建議**：列入「需要 Leader 裁決的事」。

## 使用者視角回饋（非缺陷，供規劃參考）

1. **新增／編輯輸入框的 Enter 鍵目前無任何效果**（不送出、也不換行，因為是單行 `<input type="text">`）：使用者可能預期打完標題按 Enter 就能新增，需改用滑鼠點擊「新增」／「儲存」按鈕。此為 r2（本機基準）已提出的既有回饋，本輪於 staging 再次驗證行為一致（未修正，亦未列為缺陷，維持沿用先前 Leader 裁決）。
2. **201 字元上限以 HTML `maxlength=200` 於輸入框層級擋下**，使用者根本無法打出第 201 個字元，因此永遠看不到 AC-001-3 描述的「送出後顯示長度超過上限錯誤」文案。這是比 AC 更嚴格的實作（結果等價：無法建立 >200 字元標題），但若日後有測試腳本或使用者期待看到明確的「超過上限」錯誤訊息，會找不到觸發路徑，建議留意此差異，非缺陷。
3. **staging 資料極不穩定**（見上方環境現象章節）：若多個 QA agent 需並行對同一 staging 測試，建議之後改為「輪流獨占時段」或為每個 agent 的自動化測試加上資料隔離（例如各自固定的標題前綴，收尾只刪自己建立的），避免互相清空對方資料造成誤判。
