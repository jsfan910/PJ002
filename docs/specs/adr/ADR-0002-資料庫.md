# ADR-0002：資料庫選 PostgreSQL 16（staging 用 Neon 免費方案），以 node-postgres ＋ 純 SQL migration 存取

<!-- 檔名：docs/specs/adr/ADR-0002-資料庫.md -->

## 背景

要解決的問題：為 2 張表（`todos`、P1 的 `users`）選一個持久化儲存體與其存取方式。

限制：

1. **NFR-006 資料持久性**：服務重新啟動或**重新部署**後，先前建立的待辦 100% 仍可查得（以 10 筆為樣本）。這一條直接排除任何「資料與運算實例共生命週期」的方案。
2. **AC-010-3**：一次新的部署完成後重新整理頁面，先前建立的資料仍存在。
3. **O-007（Leader 裁決）**：識別碼採 **UUID**，不可猜測。
4. **NFR-007 容量**：500 筆待辦下清單 API 回應 < 2 秒。
5. **NFR-001 效能**：清單查詢 P95 < 500ms／10 併發。
6. 免費額度可部署；憑證由使用者自行設定；本機可離線驗證（`docker compose up` 即可跑起相同的資料庫）。
7. **NFR-008**：未參與者 15 分鐘內在 Windows 11 把應用跑起來 —— 本機資料庫的安裝步驟不能太長。
8. 我在審核 T-0003 時記下的待收斂點：**BR-005「依 createdAt 由新到舊」未定義同秒並列時的次序**，需在本層解決。

對應 UC：UC-001 ~ UC-007（待辦 CRUD 與篩選）、UC-012 ~ UC-014（P1 使用者與資料隔離）。

## 選項

### 資料庫產品

| 選項 | 優點 | 缺點 | 成本 |
|---|---|---|---|
| **A. PostgreSQL 16；staging 用 Neon Serverless Postgres 免費方案，本機用 `postgres:16-alpine` 容器** | 資料與運算實例**完全分離**，重新部署不觸碰資料，直球滿足 NFR-006／AC-010-3；Neon 免費方案（0.5 GB 儲存）**沒有到期日**，適合長期跑的 Phase 1 試跑；原生 `uuid` 型別與 `gen_random_uuid()`（pgcrypto／PG13+ 內建）直接支撐 O-007；本機以官方容器映像取得**與 staging 完全相同的方言**，無 dev/prod 漂移；`docker compose up` 一行跑起來，NFR-008 風險低 | 需要多管一組憑證（`DATABASE_URL`）；Neon 免費方案的運算會在閒置後自動暫停，冷啟約 0.5 秒，需以連線池與健康檢查保溫 | 免費。0.5 GB 遠大於 500 筆待辦（約 100 KB） |
| B. SQLite 檔案 ＋ 平台持久磁碟 | 零額外服務、零額外憑證、最省事 | **資料與運算實例同生命週期**：多數免費方案的容器檔案系統是暫時的，重新部署即清空，直接違反 NFR-006；要持久磁碟通常得付費；且單檔鎖在 10 併發（NFR-001）下寫入會排隊 | 免費但**不滿足硬需求**，直接淘汰 |
| C. MongoDB Atlas 免費方案（M0） | 免費層永久、512 MB | 本資料模型是兩張強型別關聯表（P1 有外鍵與唯一索引），文件資料庫的優勢用不上；`User.email` 唯一性與 `Todo.ownerId` 外鍵要靠應用層自律，增加 BR-023／BR-024 被違反的風險；本機以容器模擬 Atlas 的行為差異較大 | 免費，但與領域模型錯配 |
| D. 平台自帶的免費 PostgreSQL（如 Render 免費 Postgres） | 與運算同一個平台，設定最少 | 該免費方案**有 30 天到期**，到期後需重建，資料會消失，與 NFR-006 的精神衝突，也會在試跑中途製造一次無謂的中斷 | 免費但有到期日，淘汰 |

### 存取方式

| 選項 | 優點 | 缺點 | 成本 |
|---|---|---|---|
| **A. `pg`（node-postgres）＋ 參數化查詢 ＋ 純 `.sql` migration 檔，由一支 20 行的 runner 依序套用** | 2 張表、6 個查詢，SQL 全部攤在眼前，qa-cr 可逐字審；無程式碼產生步驟，Docker 映像小、`docker build` 快；migration 是純 SQL，dev-be 與 dev-ops 都看得懂；參數化查詢（`$1`、`$2`）是 `pg` 的標準用法，SQL injection 風險可由 CR 以「有無字串拼接」一眼判定 | 需自行寫 row → 物件的對應（本案 2 個實體、9 個欄位，約 30 行）；沒有編譯期的 schema 型別檢查 | 最低 |
| B. Prisma ORM | 型別安全、migration 工具成熟、訓練資料多 | 需要 `prisma generate` 建置步驟與平台專屬的引擎二進位檔，Docker 多階段建置要處理 binary target，是免費方案部署最常見的卡關點；映像顯著變大；對 2 張表而言投入產出比低 | 中 |
| C. TypeORM／Sequelize | 生態成熟 | 裝飾器與設定慣例多，對「規模刻意小」是額外心智負擔；migration 產生的 SQL 不直觀，不利 CR | 中 |

## 決定

**資料庫選 A：PostgreSQL 16 —— staging 使用 Neon Serverless Postgres 免費方案，本機使用 `postgres:16-alpine` 容器（由 `docker-compose.yml` 帶起）。存取方式選 A：`pg`（node-postgres）＋ 參數化查詢 ＋ 純 `.sql` 順序 migration。**

配套的具體決定：

1. **識別碼**：`todos.id` 與 `users.id` 皆為 `uuid`，預設值 `gen_random_uuid()`（PostgreSQL 13 起內建，不需額外擴充）。落實 O-007 的 Leader 裁決。
2. **排序 tie-break（收斂我在 T-0003 審核時記下的瑕疵）**：`created_at` 型別為 `timestamptz`，PostgreSQL 的 `timestamptz` 原生為**微秒精度**；清單查詢一律 `ORDER BY created_at DESC, id DESC`。加上 `id` 作為次要排序鍵後，即使兩筆的時間戳完全相同（例如以腳本批次建立 NFR-007 的 500 筆），順序仍是**決定性的**，測試斷言可以寫死。BR-005 的「由新到舊」語意不變。
3. **索引**：`idx_todos_created_at_desc` 為 `(created_at DESC, id DESC)`（P0 的清單查詢與排序）；P1 追加 `idx_todos_owner_created` 為 `(owner_id, created_at DESC, id DESC)`（BR-022 要求先以使用者過濾再套狀態篩選）。`users.email` 以 `UNIQUE` 約束落實不變量 I-5。狀態篩選（`is_completed`）**不另建索引**：500 筆的資料量（NFR-007）下選擇度低，額外索引只增加寫入成本。
4. **不用 ORM 的安全配套**：**禁止任何形式的 SQL 字串拼接**，一律使用 `pg` 的參數化查詢；此條寫入 SD 第 6 章「輸入驗證」與 CR 檢查清單，qa-cr 以「repository 層是否出現樣板字串插值」為單一判準。
5. **migration 策略**：檔名 `NNN_描述.sql` 順序遞增，**只前進不回退**（forward-only）；以 `schema_migrations` 表記錄已套用的版本。程式碼回滾（見 `06_部署架構與CICD.md` 第 5 章）因此**不需要**回滾資料庫，這是刻意的設計 —— 免費方案沒有可靠的時間點還原。
6. **欄位命名**：資料庫層一律 `snake_case`（`is_completed`、`created_at`、`owner_id`），API 層一律 `camelCase`（`isCompleted`、`createdAt`、`ownerId`），轉換只發生在 repository 層單一位置。
7. **`updated_at`（O-008）**：**加入資料表**作為維運用欄位，但**不出現在 API 回應契約、不呈現給使用者**。符合 SA 第 7 章 O-008 的保守假設與 Leader 裁決；不構成擴大範圍，因為它不是任何 AC 的驗收標的。

## 後果

- 正面：
  - NFR-006 與 AC-010-3 由架構本身保證（資料庫是外部託管服務），不依賴任何部署腳本的正確性。
  - 本機與 staging 使用同一個 PostgreSQL 主版本，`docker compose up` 即得到與 staging 相同方言的資料庫，離線驗證與 NFR-008 同時受益。
  - 排序有決定性的 tie-break，測試團隊可對 500 筆情境寫死斷言。
  - 沒有 ORM 的產生步驟，`docker build` 單純，映像小，冷啟快（間接幫到 NFR-001／NFR-003）。
- 負面／要承擔的：
  - 多一組憑證 `DATABASE_URL` 要由使用者自行設定（Epic 限制：agent 不得索取或代填）。已列入 `06_部署架構與CICD.md` 第 4 章環境變數清單。
  - Neon 免費方案閒置後運算會自動暫停，首次連線約 0.5 秒冷啟。對策：應用啟動即建立連線池（`pg.Pool`，`max: 5`），且 NFR-003 的 5 分鐘健康檢查同時具備保溫效果。若 NFR-001 的 P95 量測受冷啟影響，量測腳本須先跑 10 秒暖身再開始取樣 —— 此點已寫入 SD 第 7 章 NFR-001 的驗證方式。
  - 手寫 SQL 的 injection 風險以「禁止字串拼接 ＋ CR 逐行檢查」控制，屬流程性控制而非技術性保證，需要 qa-cr 確實執行。
  - Neon 免費方案 0.5 GB 上限：本案上限 500 筆（NFR-007），約 100 KB，餘裕充足，無需監控儲存用量。
- 對其他文件的影響：
  - DB：`05_資料庫設計.md` 全篇（ERD、欄位表、DDL、索引、敏感欄位）。
  - SD：第 2 章技術選型表、第 3 章 `todo-repository`／`db-migration` 模組、第 4 章資料模型摘要、第 6 章「禁止字串拼接」、第 7 章 NFR-001／006／007 的對策。
  - API：`createdAt` 以 RFC 3339／ISO 8601 含時區的字串回傳（BR-004）；`id` 的 schema 為 `format: uuid`。
  - 部署：新增環境變數 `DATABASE_URL`；pipeline 增加一個在部署前套用 migration 的階段；`docker-compose.yml` 納入 `postgres:16-alpine`。
