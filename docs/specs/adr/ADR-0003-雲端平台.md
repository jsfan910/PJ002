# ADR-0003：staging 雲端平台選 Render Web Service（Docker runtime，免費方案）＋ Neon Postgres；CI/CD 用 GitHub Actions

<!-- 檔名：docs/specs/adr/ADR-0003-雲端平台.md -->

## 背景

要解決的問題：US-010 要求一個**雲端 staging 環境**，讓驗收者用瀏覽器打開、逐條驗收 P0 使用者故事（UC-010），並讓監測排程器定時量測存活（UC-011）。

限制：

1. **免費額度可部署**（Epic 限制）。
2. **憑證與雲端帳號由使用者提供，agent 不得索取或代填**（Epic 限制）。
3. **可離線驗證**：本機 `docker build` 或 IaC plan 就要能驗。
4. **CI/CD 用 GitHub Actions**（Epic 限制，不是本 ADR 的選項）。
5. 指令須可在 Windows 11 的 Git Bash 或 PowerShell 執行。
6. DevOps 只有 **1–2 張工作卡**的預算。
7. **O-004（Leader 裁決）**：前端與 API 同源，故平台上只需**一個**對外服務。

對應 NFR／AC：

- **AC-010-2／BR-025／NFR-002①**：一律 HTTPS，HTTP 須導向 HTTPS。
- **AC-010-3／NFR-006**：重新部署後資料仍在。
- **AC-010-5／NFR-003**：健康檢查端點回 200；連續監測成功率 ≥ 99%（每 5 分鐘一次）；**單次部署造成的不可用時間 < 60 秒**。Leader 對 O-009 裁決 Gate 2 採 **24 小時**採樣。
- **NFR-001**：P95 < 500ms／10 併發。
- **NFR-008**：未參與者 15 分鐘內在本機跑起來，並可重現一次 staging 部署。

## 選項

| 選項 | 優點 | 缺點 | 成本 |
|---|---|---|---|
| **A. Render Web Service（Docker runtime，Free 方案）＋ Neon Postgres（Free）** | 免費方案**不需綁信用卡**即可建立 Web Service，對「憑證由使用者自行設定」最友善；原生支援 **Dockerfile 部署**，本機 `docker build` 成功幾乎等同雲端建置成功，離線驗證最有效；自動配發 `*.onrender.com` 的 **HTTPS 憑證並自動把 HTTP 導向 HTTPS**，AC-010-2／BR-025 由平台直接滿足，零工作量；支援 **health check path ＋ 零停機輪替**（新實例通過健康檢查才切流量），直接服務 NFR-003 的「不可用時間 < 60 秒」；`render.yaml`（Blueprint）是宣告式 IaC，可進版控、可離線做 schema 檢查；部署觸發只需一個 **Deploy Hook URL**，GitHub Actions 端一行 `curl` 即可，DevOps 卡數壓得住 | Free 方案在**連續 15 分鐘無流量後會休眠**，冷啟約 30–50 秒；Free 方案無持久磁碟（本案不需要，資料在 Neon）；單一區域 | 免費 |
| B. Fly.io（Machines ＋ Fly Postgres） | Docker 原生、全球佈署、有持久磁碟 | 目前**建立帳號即要求信用卡**，與「憑證由使用者提供」的體驗摩擦大；`fly.toml` ＋ Machines 的心智模型較重，DevOps 1–2 張卡吃緊；Fly Postgres 是自管叢集，維運責任回到團隊，與 NFR-006 的風險取向相反 | 有免費額度但需綁卡 |
| C. Cloudflare Workers ＋ D1 | 免費額度極慷慨、全球邊緣、無冷啟 | 執行環境**不是標準 Node.js**（Workers runtime），Fastify 與 `pg` 皆不能直接使用，等於推翻 ADR-0001 與 ADR-0002；**無法用 `docker build` 離線驗證**，違反硬約束；D1 是 SQLite 方言，與本機開發環境不一致 | 免費，但與三項硬約束衝突 |
| D. Google Cloud Run ＋ Neon | 容器原生、永久免費額度（每月 200 萬次請求）、規模彈性佳、冷啟快 | **必須先啟用計費帳戶並綁信用卡**才能使用，即使實際不扣款；IAM 與服務帳號金鑰的設定步驟多，對 DevOps 1–2 張卡與 NFR-008 的 15 分鐘門檻都是壓力；`gcloud` CLI 在 Windows 的安裝是額外前置 | 免費額度內免費，但需綁卡 |
| E. Vercel／Netlify（Serverless Functions） | 前端託管體驗最佳、免費額度大 | 以無伺服器函式承載 Fastify 需要 adapter，**全站 Basic Auth 的中介層（BR-016）與 `/health` 豁免（BR-017）要改用平台專屬的 Edge Middleware**，可攜性差且離線無法完整驗證；長連線的資料庫連線池在函式模型下需改用 serverless driver | 免費，但認證約束實作繞路 |

## 決定

**選 A：staging 部署於 Render Web Service（Docker runtime、Free 方案、單一服務同時供應單頁前端與 API），資料庫為 Neon Serverless Postgres（Free 方案，見 ADR-0002）。CI/CD 為 GitHub Actions（Epic 指定），以 Deploy Hook 觸發 Render 部署。**

理由，逐條對上硬約束：

1. **不需綁信用卡**即可完成整條路徑（Render Free ＋ Neon Free），是所有選項中對「憑證與帳號由使用者提供」摩擦最小的一組。使用者只需在兩個平台各建一個免費帳號，貼三個值進 GitHub Secrets。
2. **離線驗證最有效**：Render 的 Docker runtime 直接吃專案根目錄的 `Dockerfile`。`docker build -t todo-app .` 在本機成功，就已經驗掉了雲端建置的絕大部分失敗原因。選項 C、E 都做不到這點。
3. **AC-010-2／BR-025 零工作量**：Render 自動配發 HTTPS 憑證並把 HTTP 301 導向 HTTPS。團隊不需要寫任何導向邏輯，也不需要管憑證更新。
4. **NFR-003 的「單次部署不可用 < 60 秒」有平台級對策**：Render 的部署流程是先啟動新實例、以設定的 health check path（本案為 `/health`）確認健康後才切換流量並關閉舊實例。只要 `/health` 正確豁免 Basic Auth（BR-017、Leader 對 O-005 的裁決），部署即為零停機，量測值遠低於 60 秒門檻。
5. **DevOps 卡數壓得住**：部署介面只有一個 Deploy Hook URL，GitHub Actions 端是一行 `curl -fsS "$RENDER_DEPLOY_HOOK_URL"`，再輪詢 `/health` 直到 200。相較選項 D 的 IAM ＋ 服務帳號金鑰，工作量差一個量級。
6. **IaC**：`render.yaml`（Blueprint）進版控，宣告服務型別、region、健康檢查路徑與環境變數**名稱**（值一律標 `sync: false`，由使用者在平台上填）。此檔可離線以 YAML 語法檢查驗證。

**對 Free 方案休眠的正面處理（不是忽略，是設計對策）**：

- Free 方案在連續 15 分鐘無流量後休眠，冷啟 30–50 秒。
- NFR-003 要求的監測本身就是**每 5 分鐘一次**對 `/health` 的請求（UC-011）。5 分鐘 < 15 分鐘，因此**監測排程器本身即為保溫機制**，服務在監測期間不會進入休眠。這不是巧合，是把量測手段同時當作可用性手段。
- 監測以 GitHub Actions 的 `schedule` 工作流實作（`cron: "*/5 * * * *"`），不引入第三方服務，無額外帳號與憑證。註：GitHub 的排程觸發在尖峰時段可能延遲數分鐘，因此該工作流每次執行**連續取樣 3 次（間隔 20 秒）**以降低單點漏測，統計時以實際取樣次數為分母。
- **殘留風險**：若監測工作流本身失效超過 15 分鐘，下一次驗收者開啟頁面會遇到一次 30–50 秒冷啟，該次請求的 P95 會遠超 NFR-001 的 500ms。對策：NFR-001 的負載量測腳本規定先暖身 10 秒再取樣（見 SD 第 7 章）；並在 `06_部署架構與CICD.md` 第 6 章把「冷啟」列為已知的告警誤報來源。此風險為免費方案的固有代價，已明確承擔，不隱藏。

## 後果

- 正面：
  - 整條交付路徑（建置 → 測試 → 部署 → 監測 → 驗收）在免費額度內走完，且不需信用卡。
  - HTTPS、導向、零停機輪替三項由平台提供，團隊不需自行實作，減少三處出錯點。
  - `Dockerfile` ＋ `render.yaml` 兩個檔案即為完整的部署定義，兩者都進版控、都可離線檢查，符合「可重現一次 staging 部署」（AC-010-4）。
  - 與 ADR-0001、ADR-0002 完全相容：標準 Node.js 執行環境、標準 PostgreSQL 連線。
- 負面／要承擔的：
  - **平台鎖定程度低但非零**：`render.yaml` 是 Render 專屬格式。緩解：應用本身只依賴 `Dockerfile` 與環境變數，換平台時只需重寫 `render.yaml`（約 30 行），應用程式碼不動。
  - **冷啟**：如上所述，以監測保溫 ＋ 量測暖身處理，殘留風險已明確承擔。
  - **單一區域、無 SLA**：Free 方案不提供可用性保證。NFR-003 的 99% 是團隊的自我量測目標，不是平台承諾。若 Gate 2 的 24 小時採樣未達 99%，應先區分是應用缺陷還是平台休眠，再決定是否升級方案。此判讀方式已寫入 SD 第 7 章 NFR-003。
  - 使用者需自行在 Render 與 Neon 各建一個免費帳號，並自行填入 Basic Auth 帳密與資料庫連線字串。**agent 不索取、不代填**；`06_部署架構與CICD.md` 第 4 章只列環境變數名稱與用途，不含任何值。
- 對其他文件的影響：
  - 部署：`06_部署架構與CICD.md` 全篇（環境清單、雲端資源、pipeline、環境變數、回滾、監控）。
  - SD：第 1 章 C4 Level 2 的容器邊界、第 2 章技術選型表、第 7 章 NFR-001／003／006 的對策與驗證方式。
  - API：`04_API規格.yaml` 的 `servers` 區塊列出 dev（`http://localhost:8080`）與 staging（`https://<service>.onrender.com`，實際值由使用者填）。
  - DB：與 ADR-0002 的 Neon 選擇一致，無額外影響。
