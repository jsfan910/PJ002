# ADR-0001：後端語言與框架選 Node.js 22 LTS + TypeScript + Fastify 5；前端不用框架

<!-- 檔名：docs/specs/adr/ADR-0001-語言框架.md -->

## 背景

要解決的問題：為 E-001 待辦事項 Web 應用選一組語言與框架，同時滿足後端 REST API（UC-001 ~ UC-007、UC-009、UC-011～UC-014）與單頁前端（UC-008）。

限制（`tasks/E-001-todo-app.md#限制` 與 Leader 裁決）：

1. 免費額度可部署、憑證由使用者自行設定。
2. **可離線驗證**：本機 `docker build` 或 IaC plan 就要能驗，不得非上雲才知道對不對。
3. 指令須可在 **Windows 11 的 Git Bash 或 PowerShell** 執行。
4. 規模刻意小：後端 3–5 張工作卡、前端 1–2 張、DevOps 1–2 張。
5. 執行本設計的是 **Sonnet 等級的開發 agent**，選型要「主流、訓練資料充足、踩坑少」，**不追求新奇**。
6. O-004（Leader 裁決）：**前端與 API 同源**，由同一個服務同時供靜態檔與 API。

對應的 NFR／UC：

- NFR-001 效能（P95 < 500ms／10 併發）、NFR-005 可維運性（**結構化日誌含時間／路徑／方法／錯誤訊息／請求識別碼**）、NFR-004 相容性（Chrome／Edge 最新兩版、Firefox 最新版 × 桌機 1280×800 與行動 390×844）、NFR-008 可安裝性（未參與者 15 分鐘內在 Windows 跑起來）。
- BR-013（輸出逸出防 XSS）、BR-014（統一錯誤結構 ＋ 5xx 結構化日誌）、BR-016／BR-017（全站 Basic Auth，`/health` 唯一豁免）。

## 選項

### 後端

| 選項 | 優點 | 缺點 | 成本 |
|---|---|---|---|
| **A. Node.js 22 LTS + TypeScript + Fastify 5** | 官方外掛 `@fastify/basic-auth`（全站保護 ＋ 單一路徑豁免）、`@fastify/static`（同源供靜態檔）、內建 pino 結構化日誌含 `reqId`，三項硬約束各有對應的一級公民支援；JSON Schema 驗證可與 OpenAPI 共用同一份定義；單一語言涵蓋前後端，開發者不需切換心智模型；Docker 映像小（alpine 約 150MB） | Fastify 的知名度略低於 Express，外掛的 TypeScript 型別偶爾需要手動標註；JSON Schema 的錯誤訊息預設較生硬，需自訂錯誤序列化器才符合 BR-014 | 低。無授權費；學習曲線約半天 |
| B. Node.js 22 LTS + TypeScript + Express 5 | 最廣為人知，訓練資料最多，Sonnet 出錯機率最低 | 結構化日誌要自行接 `pino-http`；Basic Auth 與路徑豁免要自行寫中介層；驗證要外掛 `zod`／`joi`；等於三項硬約束都要手工黏合，黏合處正是最容易出錯的地方 | 低，但手工黏合的程式碼量與 CR 成本較高 |
| C. Python 3.12 + FastAPI | 自動產生 OpenAPI、Pydantic 驗證極強；生態成熟 | 前端仍需 JavaScript，團隊要維護兩種語言與兩套工具鏈（pip／npm），違反「規模刻意小」；Windows 上的虛擬環境與路徑問題較 Node 多，威脅 NFR-008 的 15 分鐘門檻；Docker 映像較大 | 中。多一條工具鏈的維護成本 |
| D. Java 21 + Spring Boot | 企業級成熟、Spring Security 開箱即用 | 對 2 張表、7 個端點的規模嚴重過重；映像大、冷啟動慢，直接威脅 NFR-001 與 NFR-003；免費額度平台的記憶體配額常放不下 | 高。與「規模刻意小」正面衝突 |

### 前端

| 選項 | 優點 | 缺點 | 成本 |
|---|---|---|---|
| **A. 原生 HTML + CSS + ES2020 vanilla JavaScript（無框架、無打包器）** | 零建置步驟，`docker build` 只需複製檔案，離線驗證最單純；沒有框架版本相容問題，NFR-004 的六組瀏覽器矩陣風險最低；`textContent` 寫入天然滿足 BR-013 逸出要求；前端 1–2 張卡的規模綽綽有餘 | 手寫 DOM 更新；狀態管理靠自律（需 SD 第 3 章明確規定單向資料流） | 最低 |
| B. React + Vite | 元件化、生態豐富 | 為 1 個頁面、4 個互動引入打包器與 node_modules，建置步驟與版本相容問題顯著提高 NFR-008 的卡關風險；與「前端 1–2 張卡」不成比例 | 中 |
| C. htmx + 伺服器端樣板 | 程式碼極少 | 與 AC-008-1「不發生整頁跳轉」及 UC-008 的前端狀態機描述需要額外論證；且 US-009 要求 API 為 JSON，會變成同時維護 JSON 與 HTML 兩種回應 | 中 |

## 決定

**後端選 A：Node.js 22 LTS + TypeScript 5 + Fastify 5。前端選 A：原生 HTML/CSS/ES2020 vanilla JavaScript，無框架、無打包器。**

理由，逐條對上硬約束：

1. **BR-016／BR-017 的「擋整站但 `/health` 豁免」**：`@fastify/basic-auth` 搭配 `onRequest` 全域 hook，於 hook 內對 `/health` 單一路徑 early-return，是官方文件即有的寫法；Express 要自己寫中介層並自行維護豁免清單，錯一個字就變成整站不設防或健康檢查被 401 擋死（後者會讓 NFR-003 與 AC-010-5 **永遠不通過**）。這一條是選 Fastify 而非 Express 的**決定性理由**。
2. **NFR-005 結構化日誌**：Fastify 內建 pino，預設每筆請求就帶 `reqId`、`req.method`、`req.url`、耗時，5xx 自動以 error 等級輸出。BR-014 要求的「時間／路徑／方法／錯誤訊息／可關聯的請求識別碼」五項**開箱即有**，不需額外程式碼。
3. **統一錯誤物件（BR-014）**：以 Fastify 的 `setErrorHandler` 單點收斂為 `{ code, message, details?, requestId }`，同時在此處剝除堆疊追蹤與 SQL 片段，一次滿足 BR-026 與 NFR-002②。
4. **驗證（BR-001／BR-002／BR-010／BR-012）**：Fastify 的路由 schema 直接使用 JSON Schema，與 `04_API規格.yaml` 的 `components.schemas` 是同一種語言，可人工對照無誤差；並以 `removeAdditional: true` 實作 BR-012「請求夾帶其他欄位一律忽略」。
5. **同源（O-004）**：`@fastify/static` 以 `root: public/` 供應單頁前端，API 掛在 `/api/v1/*`，同一個服務、同一個來源，CORS 問題自然消失（詳見 ADR-0004）。
6. **可離線驗證**：多階段 `Dockerfile`（builder 跑 `npm ci` ＋ `tsc`，runtime 只留 `dist/`、`public/` 與正式依賴），`docker build .` 在 Windows 的 Git Bash 或 PowerShell 皆可執行，不需任何雲端帳號。
7. **不追求新奇**：Node LTS ＋ TypeScript ＋ Fastify ＋ 原生前端全部是有多年歷史的主流選擇，無任何前沿或實驗性技術。

版本釘選（避免「最新版」漂移造成不可重現）：Node.js `22-alpine`（LTS）、TypeScript `~5.6`、Fastify `^5`。CI 與 Dockerfile 使用同一個 Node 主版本。

> 註：本設計的執行環境為 Node.js 22 LTS。本機目前安裝的是 Node v24.15.0，可用於離線的 lint 與語法檢查，但 Dockerfile 與 CI 一律釘選 22-alpine，兩者不衝突。

## 後果

- 正面：
  - 三項最容易出錯的硬約束（Basic Auth 豁免、結構化日誌、統一錯誤物件）各自落在框架的一級公民能力上，Sonnet 等級開發者按文件寫即可，不需自創黏合層。
  - 單一語言（TypeScript／JavaScript）涵蓋前後端與建置腳本，工具鏈只有 npm 一條，直接支撐 NFR-008 的 15 分鐘門檻。
  - 前端無建置步驟，六組瀏覽器相容性矩陣（NFR-004）的變因最少。
- 負面／要承擔的：
  - Fastify 的訓練資料量少於 Express，開發卡的「背景與限制」欄**必須附上官方外掛名稱與版本**（`@fastify/basic-auth`、`@fastify/static`、`@fastify/jwt`），避免開發者臨場自行發明中介層。此項已寫入 SD 第 3 章模組表。
  - 原生前端需要自律的單向資料流，否則 BR-011（狀態變更後以目前篩選重新計算清單）容易寫成散落各處的 DOM 補丁。SD 第 3 章已把前端切成 `api-client` → `todo-store` → `todo-view` 三層並規定「只有 store 可改狀態，view 只讀」。
  - 不使用 ORM 的取捨屬資料庫層，見 ADR-0002。
- 對其他文件的影響：
  - SD：第 2 章技術選型表、第 3 章模組表（Fastify 外掛對應到具體模組）、第 6 章（錯誤處理器與 Basic Auth hook 的落點）、第 8 章目錄結構。
  - API：`04_API規格.yaml` 的 schema 與 Fastify 路由 schema 為同一套 JSON Schema，改一邊要同步另一邊。
  - 部署：Dockerfile 為 node:22-alpine 多階段；環境變數 `NODE_ENV`、`PORT`、`LOG_LEVEL` 由本決策引入。
  - DB：不影響（見 ADR-0002）。
