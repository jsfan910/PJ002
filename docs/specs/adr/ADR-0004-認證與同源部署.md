# ADR-0004：全站 Basic Auth 在應用層實作、`/health` 為唯一豁免路徑；前端與 API 同源部署、不啟用 CORS

<!-- 檔名：docs/specs/adr/ADR-0004-認證與同源部署.md -->

## 背景

本 ADR 處理三個**互相糾纏**的約束。它們單看都簡單，湊在一起會互相破壞，所以合成一份決策紀錄，而不是分散在三處。

1. **Q-008（Leader 裁決）**：P0 階段 staging 以 **HTTP Basic Auth 擋整站（頁面 ＋ API）**，單一共享帳密由使用者放平台 secrets；可在應用層或反向代理層實作；P1 上線後由 JWT 取代。對應 BR-016。
2. **O-005（Leader 裁決）**：**健康檢查端點豁免 Basic Auth**，且 plan-sd 須在 SD 第 6 章與部署設計**明列它是唯一未保護路徑**。對應 BR-017、AC-010-5、NFR-003。
3. **O-004（Leader 裁決）**：**前端與 API 同源**。對應 AC-009-5（CORS 不得用萬用字元 `*`）、BR-015。

糾纏點在於：

- 若 Basic Auth 擋整站而**不**豁免 `/health`，監測排程器一律取得 401，**AC-010-5 與 NFR-003 永遠不通過**（SA 已於 UC-011 例外流程 E3 標為致命交互）。
- 若前端與 API **跨來源**，瀏覽器的跨來源請求必須帶 Basic Auth 憑證，伺服器就得同時回具名的 `Access-Control-Allow-Origin` 與 `Access-Control-Allow-Credentials: true`，且預檢請求（`OPTIONS`）本身**不帶** `Authorization` 標頭 —— 預檢會先被 Basic Auth 擋成 401，前端在 staging 上將完全無法呼叫 API。SA 已於 O-004 標為**阻擋級**。
- 我在審核 T-0003 時另記下：**AC-009-5 的 Given 前提是「前端與 API 部署於不同來源」，與 O-004 的同源裁決不是矛盾，但需要一個明確說法**，否則測試團隊不知道怎麼驗這條 AC。本 ADR 一併收斂。

## 選項

### 議題一：Basic Auth 實作在哪一層

| 選項 | 優點 | 缺點 | 成本 |
|---|---|---|---|
| **A. 應用層：Fastify 全域 `onRequest` hook ＋ `@fastify/basic-auth`，於 hook 內對 `/health` early-return** | 保護規則與豁免規則**寫在同一個檔案的同一個函式裡**，是否有第二個未保護路徑，看這一段就知道，CR 成本最低；本機 `docker run` 即可完整驗證（帶憑證 200／不帶 401／`/health` 200），不需上雲；換平台不需重寫 | 保護邏輯進入應用程式碼，理論上比獨立代理層多一層被繞過的可能（實務上本案只有一個入口，無此路徑） | 低 |
| B. 反向代理層（Cloud Run 容器內前置 nginx／Caddy 容器） | 應用程式碼完全乾淨；保護在應用之外 | 免費方案的單一 Web Service 內要多跑一個代理程序，等於在容器內做程序管理，違反「規模刻意小」；豁免規則寫在 nginx 設定，與應用路由分處兩檔，容易漂移；本機驗證要同時跑兩個程序 | 中 |
| C. 平台內建的存取保護 | 零程式碼 | Cloud Run **不提供**內建的 Basic Auth／存取保護；且平台級保護通常無法對單一路徑開洞，`/health` 豁免做不到，直接與 O-005 衝突 | 不可行 |

### 議題二：前端與 API 的來源關係

| 選項 | 優點 | 缺點 | 成本 |
|---|---|---|---|
| **A. 同源：單一 Cloud Run 服務，`@fastify/static` 供應 `public/`，API 掛在 `/api/v1/*`** | **CORS 問題不存在**（沒有跨來源請求就沒有預檢，也就沒有「預檢被 Basic Auth 擋成 401」的死結）；只有一組網址、一組憑證、一個部署目標，DevOps 卡數最省；Basic Auth 一次把頁面與 API 都擋住，完全符合 Q-008 的「擋整站」 | 前端與後端同進同出，改一個字串也要重新部署整個服務（本案規模下不是問題）；無 CDN 加速（本案僅三個靜態檔，不需要） | 最低 |
| B. 跨來源：前端放靜態託管（Netlify／Cloudflare Pages），API 放 Cloud Run | 前端可獨立部署、有 CDN | 必須處理預檢與 Basic Auth 的死結（見上）；兩組網址、兩個部署目標、兩份 CI 設定；驗收者要記兩個網址；CORS 具名來源設定錯一次就整站不能用 | 高，且與 O-004 裁決相反 |

## 決定

**議題一選 A：Basic Auth 在應用層以 Fastify 全域 `onRequest` hook 實作，`/health` 為唯一豁免路徑。**
**議題二選 A：前端與 API 同源，單一 Cloud Run 服務同時供應靜態檔與 API，不啟用 CORS。**

具體規則（開發與 CR 的單一判準）：

1. **保護範圍**：`onRequest` 全域 hook 掛在 Fastify 根實例上，涵蓋**所有**路由，包含 `GET /`、靜態資產與全部 `/api/v1/*`。未帶或帶錯憑證一律回 `401` 並附 `WWW-Authenticate: Basic realm="staging"`，使瀏覽器彈出原生認證提示（UC-010 主要流程第 1 步）。
2. **唯一豁免**：hook 的第一行是
   `if (req.url === "/health") return;`
   —— **只比對完全相等的字串，不用前綴比對、不用萬用字元、不用正則**。前綴比對會讓 `/healthz-secret`、`/health/../api/v1/todos` 之類的路徑意外落入豁免，是這類設計最常見的漏洞。
3. **豁免路徑清單就是一行程式碼**：SD 第 6 章與 `06_部署架構與CICD.md` 皆明列「`GET /health` 是**唯一**未保護路徑」。新增任何豁免路徑視為**規格變更**，須走規格變更請求任務卡，不得由開發者自行決定。
4. **`/health` 的回應內容受限**：只回 `{"status":"ok"}`（固定字面值），**不得**回傳版本號、commit SHA、資料庫連線狀態、環境變數或任何內部細節。理由：它是唯一對全網公開的路徑，回傳越多，資訊洩漏面越大（BR-017 後半段、BR-026）。
   - 因此 `/health` **不檢查資料庫**。它回答的是「這個程序活著且能回應 HTTP」，不是「整個系統健康」。這正是 Cloud Run 零停機輪替與 NFR-003 需要的語意：資料庫短暫抖動不應觸發整個服務被判定為死亡並重啟。
5. **CORS**：**完全不註冊 `@fastify/cors`**。同源部署下沒有跨來源請求，因此不會回應任何 `Access-Control-Allow-Origin` 標頭，自然滿足 BR-015「不得使用萬用字元 `*`」—— 因為根本沒有這個標頭。
   - 預留通道：環境變數 `CORS_ALLOWED_ORIGINS` 保留在清單中但**預設為空**；只有當未來真的需要跨來源（例如 Epic 提到的行動 App 從瀏覽器端呼叫）時，才由該變數帶入**具名來源**並同時開啟 `credentials: true`。空值即代表「不註冊 CORS 外掛」。
6. **AC-009-5 的驗證方式（收斂 T-0003 審核記下的第 2 點）**：該 AC 的 Given 前提「前端與 API 部署於不同來源」在本設計下**不成立**，故以其**規範意圖**驗證，判準為兩條，兩條都必須通過：
   - (a) 對任一 API 端點的回應**不得**出現 `Access-Control-Allow-Origin: *`。
     驗證：`curl -sSI -u "$USER:$PASS" https://<staging>/api/v1/todos | grep -i access-control-allow-origin` → **預期無輸出**。
   - (b) 單頁前端呼叫 API 時**不發生跨來源請求**（頁面來源與 API 來源相同）。
     驗證：瀏覽器 DevTools Network 分頁中，`/api/v1/*` 請求的 Origin 與頁面網域相同，且無 `OPTIONS` 預檢請求。
   此判準已同步寫入 `docs/specs/traceability.md` 與 SD 第 7 章 NFR-002。
7. **P1 的接續**：P1 上線時，Basic Auth hook 整段移除，改由 `@fastify/jwt` 對 `/api/v1/todos*` 做授權（BR-020），`/api/v1/auth/register` 與 `/api/v1/auth/login` 為公開端點，`/health` 維持公開。**移除 Basic Auth 與導入 JWT 必須是同一次部署**，否則中間會出現一段完全不設防的視窗。此點為 P1 的部署前置條件，已寫入 SD 第 9 章開放問題。

## 後果

- 正面：
  - 三個互相糾纏的約束一次解開：擋整站（Q-008）、`/health` 豁免（O-005）、同源（O-004）彼此不再衝突，且 CORS 死結從根本上消失。
  - 「唯一未保護路徑」可由**一行程式碼**驗證，CR 與安全檢查的成本降到最低。
  - 本機 `docker run` 即可完整驗證認證行為（三個 curl 指令），不需要雲端帳號，符合離線驗證的硬約束。
  - 只有一個部署目標、一組網址、一組憑證，DevOps 1–2 張卡的預算守得住。
- 負面／要承擔的：
  - **`/health` 對全網公開**。承擔方式：回應固定為 `{"status":"ok"}`，不含任何內部資訊；且該端點不觸碰資料庫，被大量請求也不會拖垮後端。此為 Leader 裁決 O-005 後的既定取捨。
  - **前端與後端同進同出**：改一行 CSS 也要重新部署整個服務。在本案（三個靜態檔、單一服務）規模下可接受；若前端日後成長，再考慮拆分並回頭改寫本 ADR。
  - **應用層保護意味著應用啟動失敗時沒有任何保護**。但應用啟動失敗時服務也不存在，無實際暴露面；Cloud Run 的零停機輪替保證舊 revision 在新 revision 通過啟動檢查前不會失去流量。
  - `CORS_ALLOWED_ORIGINS` 這個空的環境變數會讓不知情者困惑。緩解：`06_部署架構與CICD.md` 第 4 章的「用途」欄明寫「預設留空＝同源部署，不註冊 CORS 外掛；填值才啟用具名來源」。
- 對其他文件的影響：
  - SD：第 6 章「認證／授權」（唯一未保護路徑的明列）、第 3 章 `auth-basic`／`health`／`static-hosting` 三個模組、第 7 章 NFR-002 與 NFR-003。
  - API：`04_API規格.yaml` 全域 `security` 為 `basicAuth`，僅 `/health` 以 `security: []` 覆寫為公開；每個端點皆定義 401 回應。
  - 部署：環境變數 `BASIC_AUTH_USER`、`BASIC_AUTH_PASSWORD`、`CORS_ALLOWED_ORIGINS`；Cloud Run 的 startup probe 路徑設為 `/health`。
  - 追溯矩陣：AC-009-5 的驗證方式改為本 ADR 第 6 點的兩條判準。
