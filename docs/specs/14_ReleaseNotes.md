# Release Notes v0.1.0：E-001 待辦事項 Web 應用

面向使用者。不寫實作細節。

> **草案狀態**：P0 全部八張開發卡（T-0011～T-0018）已合併 `main`，功能完整；**staging 雲端環境尚未建立**（等待使用者提供 GCP 專案與 GitHub repo，見下方「升級／部署注意事項」）。待測試階段（T-0020～T-0023）完成並通過 Gate 2 後，由 dev-tl 把本檔的 `status` 改為 `released` 並補上實際 staging 網址。

## 新功能

- **新增待辦**（US-001）：在首頁輸入框打字、按「新增」即可建立一筆待辦。標題會自動去掉前後空白；空白或超過 200 字元的標題會被擋下並在畫面上顯示可讀的錯誤訊息，不會存進資料庫。
- **檢視待辦清單**（US-002）：一進站就看得到全部待辦，**新的在上、舊的在下**。清單為空時會顯示「目前沒有任何待辦事項，新增一筆開始吧。」，不是一片空白。
- **編輯待辦**（US-003）：每筆待辦旁有「編輯」，可就地改標題並「儲存」或「取消」。改成空白會被擋下且原標題保持不變；編輯不會改變建立時間與完成狀態。
- **刪除待辦**（US-004）：按「刪除」會先跳出確認視窗，**確認後才真的刪除**；按取消則完全不動。刪除是永久的，無法復原。
- **切換完成／未完成**（US-005）：點核取方塊即可切換，已完成的標題會加上刪除線。狀態立刻存檔，重新整理頁面後仍在。
- **依狀態篩選**（US-006）：「全部／未完成／已完成」三個按鈕。**篩選不會寫進網址、也不會被記住** —— 重新整理頁面一律回到「全部」。篩選結果為空時會顯示對應的空狀態提示。
- **顯示建立時間**（US-007）：每筆待辦顯示 `yyyy-mm-dd HH:mm` 格式的建立時間，**自動換算成你電腦所在的時區**，不使用「3 分鐘前」這類相對時間。
- **單頁操作**（US-008）：新增、清單、篩選全部在同一頁完成，任何操作都不會整頁跳轉或重新整理。操作進行中會顯示「載入中…」；**伺服器連不上或回報錯誤時，畫面會顯示可讀的訊息與「重試」按鈕，先前的資料仍留在畫面上，不會卡死或變空白**。手機（375px 寬）與桌機（1280px 寬）皆不會產生橫向捲軸，按鈕點擊區皆達 44×44。
- **REST API**（US-009）：提供 `/api/v1/todos` 五個端點（建立、查詢清單、查詢單筆、更新、刪除），可用 curl 或任何非瀏覽器用戶端直接操作，回應為 JSON、狀態碼語意正確（建立 201、刪除 204、驗證失敗 400、查無資料 404），錯誤一律是統一格式的錯誤物件。端點清單見 `docs/specs/04_API規格.yaml`。
- **存取保護**：整站以 HTTP Basic Auth 保護，**只有健康檢查端點 `/health` 不需要帳密**。第一次開啟網站時瀏覽器會要求輸入帳號密碼。
- **健康檢查與監測**（US-010 部分）：`/health` 回 `{"status":"ok"}`；staging 上線後會有排程每 5 分鐘自動取樣三次，作為可用率的量測來源。

## 已知問題

| # | 問題 | 影響 | 繞過方式 |
|---|---|---|---|
| 1 | **staging 雲端環境尚未建立**（US-010 全部 AC 未驗） | 目前只能在本機執行，無法用瀏覽器開啟雲端網址驗收；回滾演練與連續 24 小時可用率量測皆未進行 | 依 `README.md`「部署與 secrets（T-0018）」章節完成一次性設定後即會自動部署。**這是使用者端的待辦，不是程式問題。** 在此之前，本機以 `docker compose up -d` 啟動即可完整操作 US-001～US-009 |
| 2 | 刪除是**硬刪除**，沒有垃圾桶或復原功能 | 誤刪的資料救不回來 | 刪除前的確認視窗即為唯一防線，請看清楚再按確定 |
| 3 | 沒有使用者帳號系統，**全站共用一組 Basic Auth 帳密、所有人看到同一份清單** | 不適合多人各自管理私人清單 | 屬 P1 範圍（US-011 之後）。P0 定位為單一團隊的共用清單 |
| 4 | 兩人同時編輯同一筆待辦時，**後儲存的會覆蓋先儲存的**，且不會有任何提示 | 多人同時操作可能遺失修改 | 避免多人同時編輯同一筆；重新整理可看到最新內容 |
| 5 | 篩選狀態不會保存，重新整理後回到「全部」 | 重整後需重新點選篩選 | 這是刻意的設計（Leader 裁決 Q-007），非缺陷 |
| 6 | 資料庫採用免費方案，閒置後首次請求可能需要多等 1～3 秒 | 久未使用時第一次開啟稍慢 | 等待即可，不影響資料 |
| 7 | 錯誤訊息區在「本地輸入驗證失敗」時也會出現「重試」按鈕 | 語意稍有混淆（重試只會重新載入清單） | 直接修正輸入內容重新送出即可 |

> 正式的缺陷編號待測試階段（T-0020 程式碼審查、T-0021 自動化測試、T-0022 UAT）產出缺陷清單後回填。

## 升級／部署注意事項

- **這是第一個版本，沒有升級路徑**，不需要資料搬遷。
- **本機執行**：依 `README.md`「快速開始」的方式一（Docker Compose）或方式二（本機 Node）。兩種方式在 Git Bash 與 PowerShell 皆已實測可用（最慢 12 秒即可 `curl /health` 回 200）。方式二需注意 `.env` 不會被自動載入，README 已附兩種 shell 的載入指令。
- **資料庫 migration 必須先 `npm run build`**（腳本讀編譯後的 `dist/db/migrate.js`），部署順序固定為 **build → migrate → deploy**。
- **staging 部署前，使用者必須自行完成下列一次性設定**（agent 不索取、不代填任何憑證）：
  1. 建立 GCP 專案並綁定計費帳戶，啟用所需 API
  2. 建立 Artifact Registry 儲存庫
  3. 設定 Workload Identity Federation（六個步驟）—— **務必把 attribute condition 限定為自己的倉庫**（例如 `assertion.repository == "<owner>/<repo>"`）。少了這一條，任何人的 GitHub 倉庫都能換取你的 GCP 憑證，這是最嚴重也最常見的設定錯誤
  4. 在 Secret Manager 建立三個 secret（`database-url`／`basic-auth-user`／`basic-auth-pass`）並授權部署服務帳號讀取
  5. 建立 Neon 資料庫專案
  6. 在 GitHub 填入 repository variables 與 secrets（完整清單與每一項的值說明見 README 的兩張表）
  逐步指令與完整表格見 `README.md`「部署與 secrets（T-0018）」。
- **倉庫可見性**：建議設為公開（本專案無機密內容，憑證一律存放於平台 secrets），公開倉庫的 GitHub Actions 分鐘數不計費，每 5 分鐘一次的健康監測不會超額。若必須私有，需把監測頻率改為每 10 分鐘並同步調整可用率的取樣分母。
- **倉庫中不存在任何憑證值**，也不使用長期服務帳號金鑰；部署權限一律以 Workload Identity Federation 換取短期憑證。
- **首次部署成功後**，請把 Cloud Run 給的 `*.run.app` 網址回填三處：GitHub repository variable `STAGING_BASE_URL`、`docs/specs/06_部署架構與CICD.md` 第 1 章環境清單、`docs/specs/04_API規格.yaml` 的 `servers` staging 項。
- **回滾**：Cloud Run 保留舊的修訂版，回滾即為一次流量切換（目標 2 分鐘內完成），指令見 `docs/specs/06_部署架構與CICD.md` §5.1 與 `scripts/rollback-staging.sh`。**回滾演練是 Gate 2 的前置條件，目前尚未執行（被憑證阻擋）。**
