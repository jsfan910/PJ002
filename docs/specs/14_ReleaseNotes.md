# Release Notes v0.1.0：E-001 待辦事項 Web 應用（P0）

面向使用者。不寫實作細節。

> **本版定位**：P0 範圍全部交付，**Gate 2 判定為「有條件通過」**（2026-09-20，使用者裁決，見下方〈Gate 2 判定與條件〉）。這代表**產品本身沒有任何已知的功能性失敗**，但有三項條件與若干已知限制要在往後追蹤。P1（US-011 使用者註冊起）以本版為基線。
>
> **staging 網址**：`https://todo-app-dpevsdhdva-de.a.run.app`
> 全站以 HTTP Basic Auth 保護，**帳號密碼不寫在任何文件或倉庫裡**，請向專案負責人索取。唯一不需帳密的是健康檢查 `/health`。

## 1. 這一版有什麼（US-001 ~ US-010）

| US | 功能 | 你會看到什麼 |
|---|---|---|
| **US-001** | **新增待辦** | 在首頁輸入框打字、按「新增」即可建立。標題自動去掉前後空白；空白或超過 200 字元會被擋下並顯示可讀的錯誤訊息，不會存進資料庫 |
| **US-002** | **檢視待辦清單** | 一進站就看得到全部待辦，**新的在上、舊的在下**。清單為空時顯示「目前沒有任何待辦事項，新增一筆開始吧。」，不是一片空白 |
| **US-003** | **編輯待辦** | 每筆旁有「編輯」，可就地改標題並「儲存」或「取消」。改成空白會被擋下且原標題不變；編輯不會改變建立時間與完成狀態 |
| **US-004** | **刪除待辦** | 按「刪除」先跳確認視窗，**確認後才真的刪除**。刪除是永久的，無法復原（見 KL-9） |
| **US-005** | **切換完成／未完成** | 點核取方塊即可切換，已完成的標題加上刪除線。狀態立刻存檔，重新整理後仍在 |
| **US-006** | **依狀態篩選** | 「全部／未完成／已完成」三個按鈕。**篩選不寫進網址、也不會被記住**，重新整理一律回到「全部」（刻意設計，見 KL-6） |
| **US-007** | **顯示建立時間** | 每筆顯示 `yyyy-mm-dd HH:mm`，**自動換算成你電腦所在的時區**，不使用「3 分鐘前」這類相對時間 |
| **US-008** | **單頁操作** | 新增、清單、篩選全在同一頁，任何操作都不會整頁跳轉或重新整理。操作中顯示「載入中…」；**伺服器連不上或回報錯誤時顯示可讀訊息與「重試」按鈕，先前的資料仍留在畫面上**，不會卡死或變空白。手機（375px）與桌機（1280px）皆無橫向捲軸，按鈕點擊區皆達 44×44 |
| **US-009** | **REST API** | `/api/v1/todos` 五個端點（建立、查清單、查單筆、更新、刪除），可用 curl 或任何非瀏覽器用戶端直接操作。回應為 JSON、狀態碼語意正確（建立 201、刪除 204、驗證失敗 400、查無資料 404），錯誤一律是統一格式的錯誤物件。端點清單見 `docs/specs/04_API規格.yaml` |
| **US-010** | **雲端 staging 環境** | 上面那個 `*.run.app` 網址即是。HTTPS、可用瀏覽器直接操作完成 US-001 ~ US-007 的全部流程；重新部署後既有資料仍在；`/health` 不需帳密即回 `{"status":"ok"}` |

**存取保護**：整站 Basic Auth，**只有 `/health` 豁免**，且豁免只認這一條字面路徑 —— `/./health`、`/%2e/health`、`//health`、`/health/`、`/HEALTH` 等變體一律 401（已逐條實打驗證）。第一次開啟網站時瀏覽器會要求輸入帳號密碼。

**可用率**：2026-09-19 17:55 ~ 2026-09-20 18:04 的連續 24 小時窗，4 個地區共 **1156 次取樣全部成功（100%）**，門檻為 99%。

**效能**（staging 實測）：清單 P95 156 ms、建立 P95 316 ms、更新 P95 159 ms、刪除 P95 317 ms，門檻分別為 500 ms／800 ms。

## 3. 已知限制

### 3.1 仍在追蹤的缺陷（皆為 S3 等級，經裁決列 P1，不擋本版發布）

| # | 問題 | 影響 | 繞過方式／現況 |
|---|---|---|---|
| **KL-1** | **D-017（開放中）**：在 staging 的真實網路延遲下，錯誤訊息偶爾（約 2 ~ 4 成機率）不顯示 —— 例如送出空白標題時，畫面可能沒有跳出提示 | 操作確實被擋下了，但你不一定知道為什麼；資料不會被寫壞 | **修正已完成並合併**（T-0038：把前端各項操作的請求序號收斂為單一「最新動作勝出」的序號，並補了 2 條釘住該時序的測試）。**但缺陷尚未正式關閉**：這個問題只在 staging 重現得出來，關閉條件是「在 staging 重跑 TC-067／TC-009 至少 5 次連續全過」，而 staging 目前無法部署新版本（見 KL-5）。**也就是說：現在打開 staging 看到的仍是修正前的版本** |
| **KL-2** | **Firefox 兩組相容性未驗**（NFR-004 為 **4／6**）：Chromium 與 Edge 在 1280×800 與 390×844 四組皆通過，Firefox 的兩組**沒有測到** | Firefox 使用者的體驗未經驗證。**這不是「Firefox 上壞掉」，是「沒測成」** | 原因為執行環境限制：測試沙盒中 Firefox 連程式都啟動不了（Windows 行程建立層級失敗，同環境下 Chromium 對照組正常），已排除二進位檔損毀與安裝路徑問題。**需要在一般的個人電腦上跑一次**，單一指令見 `docs/reports/20260920-1901-AT-E001-r4-firefox.md`。追蹤卡 T-0041（blocked） |
| **KL-3** | **D-014（開放中）**：資料庫初始化沒有互斥機制，若對一個全新資料庫**同時**啟動兩個以上的應用實例，其中一個會啟動失敗並結束 | 目前設定為單一實例、且閒置時縮到 0，**實際碰不到**。只有未來調高實例數又同時換新資料庫時才會遇到 | 依序啟動即可，或等待 P1 隨第二份 migration 一併處理 |

### 3.2 量測與環境的限制

| # | 項目 | 說明 |
|---|---|---|
| **KL-4** | **NFR-007 的「前端可互動」子項只在本機量過** | 容量目標是「500 筆待辦下，清單 API < 2 秒、前端可互動 < 3 秒」。**清單 API 已在 staging 實測**（714 筆、中位數 116 ms，通過）；**前端可互動 166 ms 則是本機量的**（502 筆），staging 上沒有在 500 筆情境下量過。實務上前端渲染與伺服器位置無關，風險低，但這是「沒量」不是「量過了」 |
| **KL-5** | **staging 目前無法部署新版本**（既有版本仍正常服務） | 部署流程在「查詢機密版本號」這一步失敗，原因是部署用的服務帳號缺少 `roles/secretmanager.viewer` 權限。**這是雲端專案的 IAM 授權，屬使用者的安全設定，不由 CI 或 agent 代執行**。補授該角色，或改在 GitHub 填入三個 `SECRET_VERSION_*` 變數（只填版本號、不填值）即可解除。做法見 `README.md`「部署與 secrets」的「前置權限（必讀）」。**在這之前，KL-1 的修正無法上 staging** |
| **KL-6** | 篩選狀態不保存，重新整理後回到「全部」 | **刻意設計**（Leader 裁決 Q-007），非缺陷 |
| **KL-7** | 沒有使用者帳號系統，**全站共用一組帳密、所有人看到同一份清單** | P0 的定位就是「單一團隊的共用清單」。多使用者屬 P1（US-011 起） |
| **KL-8** | 兩人同時編輯同一筆待辦時，**後儲存的覆蓋先儲存的**，且不會有提示 | 避免多人同時編輯同一筆；重新整理可看到最新內容 |
| **KL-9** | 刪除是**硬刪除**，沒有垃圾桶或復原 | 刪除前的確認視窗即為唯一防線 |
| **KL-10** | 資料庫採免費方案，閒置後首次請求可能多等 1 ~ 3 秒 | 等待即可，不影響資料 |
| **KL-11** | 錯誤訊息區在「本地輸入驗證失敗」時也會出現「重試」按鈕 | 語意稍有混淆（重試只會重新載入清單）。直接修正輸入重新送出即可 |

## 4. 升級／部署注意事項

- **這是第一個版本，沒有升級路徑**，不需要資料搬遷。
- **本機執行**：依 `README.md`「快速開始」的方式一（Docker Compose，實測 27 秒）或方式二（本機 Node，實測 14 秒）。兩種方式在 Git Bash 與 PowerShell 皆已實測可用。方式二需注意 `.env` 不會被自動載入，README 附了兩種 shell 的載入指令。
- **資料庫 migration 必須先 `npm run build`**（腳本讀編譯後的 `dist/db/migrate.js`），部署順序固定為 **build → migrate → deploy**。
- **部署一次新版本**：推上 `main` 且 CI 全綠即自動觸發 staging 部署。**目前此路徑被 KL-5 擋住**，解除方式見該列。
- **倉庫中不存在任何憑證值**，也不使用長期服務帳號金鑰；部署權限一律以 Workload Identity Federation 換取短期憑證。機密一律由 Secret Manager 注入，且**釘定具體版本號**（不再使用 `latest`，避免首個修訂版解析到舊值）。
- **發布前請輪換 staging 的 Basic Auth 帳號密碼**（Gate 2 條件 C-2）。
- **回滾**：首選是把 Cloud Run 的流量切回前一個修訂版，目標 2 分鐘內完成（實際演練為 **9.7 秒／10.4 秒**，兩次切換期間 `/health` 皆 200）。完整程序、備選方案（以 git 回復並重新部署）與資料庫層的處置見 **`docs/specs/06_部署架構與CICD.md` 第 5 章「回滾程序」**（§5.1 首選、§5.2 備選、§5.3 資料庫層、§5.4 演練紀錄）；可直接執行的腳本為 `scripts/rollback-staging.sh`。
