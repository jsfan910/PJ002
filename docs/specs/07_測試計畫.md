# 測試計畫：E-001 待辦事項 Web 應用

本計畫的唯一功能是「判斷這個版本能不能過 Gate 2」。判斷依據只有三樣：第 4 章的退出準則、各報告的實際數據、缺陷清單（`docs/specs/24_缺陷清單.md`）。
測試案例本體在 `docs/specs/20_測試案例.md`（TC-001 ~ TC-123）；每條 TC 對應哪個 US／AC 見該檔與 `docs/specs/traceability.md` 主表 TC 欄。

規格已凍結（Gate 1 通過 2026-09-19）。本計畫**不新增、不放寬任何需求**；所有判準皆回指 SRS 的 AC／NFR、SA 第 5 章的 BR、SD 第 6 章的錯誤碼與安全設計、`traceability.md`「特殊驗證方式的 AC」表。

## 2. 測試層級與負責

| 層級 | 負責 | 工具 | 位置 | 何時跑 |
|---|---|---|---|---|
| 單元（unit） | dev-be / dev-fe（撰寫）、qa-cr（審） | `node --test`（SD 第 8 章目錄結構） | `tests/unit/` | 每次 PR 與 push to main，`ci.yml` 的 unit 階段；失敗阻擋合併 |
| 整合 / API contract（integration） | qa-at | `node --test` ＋ GitHub Actions service container 起 `postgres:16-alpine`；`curl` 用於 staging 側判準 | `tests/integration/` | `ci.yml` 的 integration 階段；失敗阻擋合併與部署 |
| E2E（e2e） | qa-at | Playwright（chromium／msedge channel／firefox 三個 project；viewport 1280×800 與 390×844） | `tests/e2e/` | 本機與 staging 各跑一次；相容性 6 組見 TC-091 |
| 效能／可用性量測（perf） | qa-lead | `autocannon`（NFR-001、NFR-007）；`monitor-health.yml` artifact 統計（NFR-003）；部署期間每 5 秒輪詢腳本 | `tests/perf/` ＋ CI artifact | staging 部署完成後；NFR-003 需連續 24 小時 |
| 安全／規格掃描 | qa-at ＋ qa-cr | `curl -sSI`（HTTPS 301、CORS 標頭、Basic Auth 401）、`grep -rn "innerHTML" public/`、`npx @redocly/cli lint docs/specs/04_API規格.yaml` | 報告內貼指令與輸出 | CR 階段與 staging 驗證階段 |
| Code Review（CR） | qa-cr | 人工審 ＋ SD 第 6 章列出的 grep 判準 | `docs/reports/*-CR-*` | 開發卡全數 review 後 |
| UAT | qa-uat | 瀏覽器（staging）、`curl`（US-009 的 API Consumer 角色） | `docs/reports/*-UAT-*` | CR 與 AT 皆通過後 |

**層級歸屬的單一判準**（避免同一件事被寫成兩個層級互推）：

- 只驗 **BE-05 / FE-03 的純函式邏輯**（不碰 HTTP、不碰資料庫）→ unit。32 條 BR 中可純邏輯驗證者一律落在此層。
- 需要**真實 HTTP 狀態碼、真實資料庫或真實 staging 回應標頭** → integration。
- 需要**真實瀏覽器的 DOM、視覺呈現與使用者互動**（不重整即可見、刪除線、載入中指示、二次確認）→ e2e。
- 需要**時間序列取樣或吞吐量數據** → perf。
- 需要**人親自操作或親自計時**（UAT 逐條、README 15 分鐘實測、API 文件可用性）→ uat，**不自動化**。

## 5. 缺陷分級

### 5.1 嚴重度

| 等級 | 定義 | 本 Epic 的具體例（取自 SA 第 5 章「違反時行為」） | 處理時限 |
|---|---|---|---|
| **S1** | 系統不可用／資料遺失／安全漏洞 | 全站 Basic Auth 失效或 `/health` 以外出現未保護路徑（BR-016、O-005）；憑證被 commit 進倉庫（BR-016）；XSS 可執行（BR-013）；SQL 字串拼接（SD 6.3）；`createdAt` 被改動（BR-003）；未帶 token 取得他人資料（BR-020、BR-022、BR-023）；重新部署後資料消失（NFR-006） | **立即，阻擋發布** |
| **S2** | 主要功能失效，無繞過 | 任一 P0 AC 不成立且無替代操作路徑：新增／編輯／刪除／切換／篩選任一不可用；不存在的識別碼回 5xx 或建立新資料（BR-009）；清單排序不符 BR-005；BR-011 的篩選重算不生效 | **本輪修，阻擋發布** |
| **S3** | 次要功能失效，有繞過 | 載入中指示缺漏（BR-030）；空狀態提示文案缺漏但畫面不空白（BR-028）；錯誤訊息可讀性不足但不洩漏內部細節；相容性 6 組中 1 組有非阻斷性版面瑕疵 | 可延後，**需 Leader 同意**並列入殘留風險 |
| **S4** | 外觀／文案 | 字型、間距、標點、非關鍵文案用詞 | 記錄即可，不擋發布 |

### 5.2 「阻擋級 CR 發現」的定義（退出準則第 3 項用）

CR 發現標為**阻擋級**的唯一判準：命中 SD 第 6 章或 SA 第 5 章中明載為「阻擋級」的任一條 —— 具體為 BR-003、BR-009（回 5xx／產生新資料）、BR-012（改動不可編輯欄位）、BR-013、BR-016（憑證入倉庫）、BR-018、BR-020、BR-022、BR-023、BR-026（回應含堆疊／SQL／路徑）、SD 6.3 的「repository 層出現樣板字串插值進 SQL」、SD 6.2 的「豁免比對非完全相等字串」。**其餘 CR 發現一律非阻擋級**，以 S3／S4 記錄。

### 5.3 缺陷成立的要件

每個缺陷必須有：嚴重度、**可重現步驟**、**對應 TC-ID**、來源（unit／integration／e2e／perf／CR／UAT）、狀態（open／fixed／verified／closed／wontfix）。
**缺少重現步驟或對應 TC 的，不算缺陷**，退回提報者補齊。S1／S2 一律由 qa-lead 提報 Leader 建修正任務卡。

### 5.4 重測規則

- S1／S2 修正後：重跑該缺陷對應的 TC ＋ 該 TC 所屬 US 的**全部 P0 TC**（避免修 A 壞 B）。
- S3／S4 修正後：只重跑該 TC。
- 任何觸及 BE-02（Basic Auth）、BE-03（錯誤處理）、BE-05（業務規則）的修正：重跑全部 integration TC，因為這三個模組是橫切單點。

**資料衛生規則**：

- staging 為測試資料，**P0 階段無真實個資**；P1 導入時一次性 `TRUNCATE`（BR-032、Q-011）。
- **任何憑證值不得出現在測試腳本、fixture、報告或截圖中**。Basic Auth 以環境變數 `$STAGING_BASIC_AUTH_USER` / `$STAGING_BASIC_AUTH_PASSWORD` 帶入；報告中的 `curl` 指令一律以變數形式呈現，不貼實值。
- 截圖前確認瀏覽器網址列與開發者工具中不含憑證字串。
