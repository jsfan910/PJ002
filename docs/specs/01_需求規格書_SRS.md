# 需求規格書（SRS）：E-001 待辦事項 Web 應用

> 本文件僅寫「已確認為事實」的需求。所有尚未確認的問題與其暫用假設集中在 `docs/specs/01a_需求澄清紀錄.md`，未經 Leader 裁決前不得視為需求。
> 本文件不指定技術棧（框架、資料庫、雲端服務）；依 Epic 限制，技術選型由 plan-sd 於 ADR 決定。

## 1. 目標與背景

- **要解決的問題**：使用者目前沒有一個可用瀏覽器直接操作的待辦管理工具。需要一個小型但完整、可在雲端 staging 實際操作的待辦事項 Web 應用，並保留未來接行動 App 的介面（REST API）。
- **目標使用者／角色**：
  | 角色 | 說明 | 適用階段 |
  |---|---|---|
  | 一般使用者（User） | 以瀏覽器管理自己的待辦事項 | P0、P1 |
  | 用戶端開發者（API Consumer） | 未來以行動 App 呼叫 REST API | P0（僅介面契約）|
  | 驗收者（UAT） | 於 staging 以瀏覽器逐條驗收 P0 使用者故事 | P0 |
- **成功指標（可量測）**：
  - S-1：P0 使用者故事（US-001 ~ US-010）於 staging 環境 UAT 全數通過，通過率 100%。
  - S-2：所有 P0 操作（新增、檢視、編輯、刪除、完成切換、篩選）可全程以滑鼠在單一頁面完成，不需鍵盤以外的輔助工具、不需重新整理頁面即見結果。
  - S-3：REST API 的 P0 端點可由非瀏覽器用戶端（例如 curl）完成與前端相同的全部待辦操作。
  - S-4：追溯矩陣孤兒檢查三項皆為「無」（Gate 1 判準）。

## 3. 使用者故事

ID 不可重用；優先級 P0（沒有就不能上）/ P1 / P2。
本章共用名詞：「待辦」=一筆使用者建立的事項，欄位定義見第 7 章；「清單頁」=US-008 定義的單一頁面。

### US-001 新增待辦（P0）

- 身為一般使用者，我想要在頁面上輸入文字並新增一筆待辦，以便把要做的事記下來。
- 驗收條件：
  - AC-001-1：Given 我在清單頁，When 我在新增輸入框輸入非空白標題並以滑鼠點擊「新增」按鈕，Then 該待辦出現在清單中，狀態為「未完成」，且不需重新整理頁面即可看到。
  - AC-001-2：Given 我在清單頁，When 我在標題為空或只有空白字元時點擊「新增」，Then 系統不建立任何待辦，並在畫面上顯示可讀的錯誤訊息（例：標題不可為空）。
  - AC-001-3：Given 我輸入的標題長度超過上限（見 Q-001 裁決值，暫定 200 字元），When 我點擊「新增」，Then 系統不建立待辦並顯示長度超過上限的錯誤訊息。
  - AC-001-4：Given 待辦建立成功，When 我檢查該筆資料，Then 它具有唯一識別碼與建立時間，且建立時間為建立當下的時間。
  - AC-001-5：Given 新增成功，When 畫面更新後，Then 新增輸入框被清空，可直接輸入下一筆。
- 備註／限制：標題以外的欄位（描述、到期日等）本輪不提供，見 Q-002。

### US-002 檢視待辦清單（P0）

- 身為一般使用者，我想要在一個頁面上看到我所有的待辦，以便掌握全部事項。
- 驗收條件：
  - AC-002-1：Given 系統中已有 N 筆待辦（N ≥ 1），When 我開啟清單頁，Then 畫面列出全部 N 筆，每筆至少顯示標題、完成狀態、建立時間。
  - AC-002-2：Given 系統中沒有任何待辦，When 我開啟清單頁，Then 畫面顯示可讀的空清單提示，不顯示錯誤。
  - AC-002-3：Given 清單頁已載入，When 我重新整理頁面，Then 先前建立的待辦仍在（資料持久化，見 NFR-006）。
  - AC-002-4：Given 清單中有多筆待辦，When 我檢視排列順序，Then 順序為建立時間由新到舊（見 Q-005 裁決值）。
- 備註／限制：本輪不分頁、不搜尋（範圍外）；清單筆數上限見 NFR-007。

### US-003 編輯待辦（P0）

- 身為一般使用者，我想要修改已建立待辦的標題，以便更正打錯或改變的內容。
- 驗收條件：
  - AC-003-1：Given 清單中有一筆待辦，When 我以滑鼠點擊該筆的「編輯」並輸入新的非空白標題後儲存，Then 清單中該筆顯示新標題，且不需重新整理頁面即可看到。
  - AC-003-2：Given 我在編輯狀態，When 我把標題清空或只留空白字元後儲存，Then 系統不更新該筆資料並顯示可讀的錯誤訊息，原標題保持不變。
  - AC-003-3：Given 我在編輯狀態，When 我點擊「取消」，Then 該筆維持原標題，且離開編輯狀態。
  - AC-003-4：Given 我成功編輯了一筆待辦，When 我檢視該筆，Then 其建立時間與完成狀態不因編輯而改變。
  - AC-003-5：Given 我嘗試編輯一筆不存在（已被刪除）的待辦，When 我送出儲存，Then 系統回覆「找不到資源」的錯誤，畫面顯示可讀訊息且不新增資料。
- 備註／限制：可編輯欄位僅「標題」，見 Q-002。

### US-004 刪除待辦（P0）

- 身為一般使用者，我想要刪除不再需要的待辦，以便清單只留下有效事項。
- 驗收條件：
  - AC-004-1：Given 清單中有一筆待辦，When 我以滑鼠點擊該筆的「刪除」並在確認提示中確認，Then 該筆從清單消失，且不需重新整理頁面即可看到。
  - AC-004-2：Given 我點擊「刪除」後出現確認提示，When 我選擇取消，Then 該筆仍在清單中。
  - AC-004-3：Given 我已刪除一筆待辦，When 我重新整理頁面，Then 該筆不再出現（刪除已持久化）。
  - AC-004-4：Given 我嘗試刪除一筆不存在（已被刪除）的待辦，When 我送出刪除，Then 系統回覆「找不到資源」的錯誤，不造成系統錯誤畫面。
- 備註／限制：刪除為不可復原（無回收桶，範圍外）；硬刪除或軟刪除的實作語意見 Q-003。

### US-005 切換完成／未完成（P0）

- 身為一般使用者，我想要把待辦標記為完成或改回未完成，以便追蹤進度。
- 驗收條件：
  - AC-005-1：Given 一筆待辦目前為「未完成」，When 我以滑鼠點擊其完成切換控制項（例如核取方塊），Then 該筆變為「已完成」，且畫面上以可辨識的方式呈現（例如刪除線或已完成標記），不需重新整理頁面。
  - AC-005-2：Given 一筆待辦目前為「已完成」，When 我再次點擊其完成切換控制項，Then 該筆變回「未完成」。
  - AC-005-3：Given 我切換了完成狀態，When 我重新整理頁面，Then 切換後的狀態仍保持（已持久化）。
  - AC-005-4：Given 我切換完成狀態，When 我檢視該筆，Then 其標題與建立時間不變。
- 備註／限制：完成時間（completed_at）是否需要記錄與顯示，見 Q-006。

### US-006 依狀態篩選（P0）

- 身為一般使用者，我想要只看「全部／未完成／已完成」其中一種，以便專注在我要處理的事項。
- 驗收條件：
  - AC-006-1：Given 清單同時有已完成與未完成待辦，When 我以滑鼠選擇「未完成」篩選，Then 畫面只列出未完成的待辦，已完成者不顯示。
  - AC-006-2：Given 同上，When 我選擇「已完成」篩選，Then 畫面只列出已完成的待辦。
  - AC-006-3：Given 同上，When 我選擇「全部」篩選，Then 畫面列出所有待辦。
  - AC-006-4：Given 我目前在「未完成」篩選下，When 我把其中一筆切換為已完成，Then 該筆即從目前清單中移除（因不符篩選條件），不需重新整理頁面。
  - AC-006-5：Given 篩選結果為零筆，When 畫面更新，Then 顯示可讀的「此篩選下沒有待辦」提示，而非空白或錯誤。
  - AC-006-6：Given 任一篩選狀態，When 我檢視畫面，Then 目前生效的篩選有明確的視覺標示。
- 備註／限制：篩選選項固定三種；篩選狀態是否需保存於網址或重新整理後保留，見 Q-007。

### US-007 顯示建立時間（P0）

- 身為一般使用者，我想要看到每筆待辦的建立時間，以便知道它擱置了多久。
- 驗收條件：
  - AC-007-1：Given 清單中有待辦，When 我檢視任一筆，Then 畫面顯示該筆的建立時間，包含日期與時分。
  - AC-007-2：Given 我新增一筆待辦，When 我檢視其建立時間，Then 該時間與我實際建立的時間相差不超過 1 分鐘。
  - AC-007-3：Given 我編輯或切換完成狀態，When 我再次檢視建立時間，Then 值不變。
  - AC-007-4：Given 我透過 API 取得待辦，When 我檢視建立時間欄位，Then 其為含時區資訊的 ISO 8601 字串（例：2026-09-19T05:29:41Z）。
- 備註／限制：顯示時區與格式（本地時區或固定時區、相對時間字樣）見 Q-004。

### US-008 單頁前端操作（P0）

- 身為一般使用者，我想要在單一網頁上用滑鼠完成所有待辦操作，以便不必學習或安裝任何東西。
- 驗收條件：
  - AC-008-1：Given 我用瀏覽器開啟應用首頁，When 頁面載入完成，Then 新增、清單、篩選控制項全部呈現在同一頁，不需切換頁面。
  - AC-008-2：Given 我在該頁，When 我依序執行新增、編輯、切換完成、篩選、刪除，Then 每個操作皆可只用滑鼠（點擊／必要的文字輸入）完成，過程中不發生整頁跳轉。
  - AC-008-3：Given 任一操作的後端請求失敗（例如伺服器回 5xx 或斷線），When 畫面更新，Then 顯示可讀的錯誤訊息，且畫面不停留在空白或凍結狀態。
  - AC-008-4：Given 頁面正在等待後端回應，When 我檢視畫面，Then 有可辨識的載入中或忙碌狀態指示。
  - AC-008-5：Given 我在 NFR-004 所列的瀏覽器與解析度下開啟頁面，When 我執行 AC-008-2 的操作序列，Then 全部可完成且版面無重疊遮蔽。
- 備註／限制：外觀不要求精美（Epic 明文），但必須可操作、可讀。

### US-009 REST API（P0）

- 身為用戶端開發者，我想要一組 REST API 能完成全部待辦操作，以便未來的行動 App 可以直接接。
- 驗收條件：
  - AC-009-1：Given staging 上的 API 服務，When 我以非瀏覽器用戶端（例如 curl）呼叫端點，Then 我可以完成建立、查詢清單、查詢單筆、更新、刪除、切換完成狀態的全部操作。
  - AC-009-2：Given 我呼叫查詢清單端點並帶入狀態篩選參數，When 回應返回，Then 只包含符合該狀態的待辦。
  - AC-009-3：Given 任一 API 回應，When 我檢視回應，Then 其 Content-Type 為 `application/json`，且 HTTP 狀態碼語意正確（建立成功 201、查詢成功 200、刪除成功 200 或 204、輸入驗證失敗 400、資源不存在 404、伺服器錯誤 5xx）。
  - AC-009-4：Given 我送出不合法的請求（缺必填欄位或標題為空），When 回應返回，Then 狀態碼為 400 且回應本文為統一格式的錯誤物件，包含可辨識的錯誤代碼與訊息。
  - AC-009-5：Given 前端與 API 部署於不同來源（origin），When 前端呼叫 API，Then 跨來源請求可成功，且 CORS 允許來源僅列出前端實際使用的來源，不使用萬用字元 `*`。
  - AC-009-6：Given API 已部署，When 我查閱交付文件，Then 有一份端點清單（路徑、方法、請求／回應範例、狀態碼）可供用戶端開發者直接使用。
- 備註／限制：端點路徑、資料欄位命名由 plan-sd 於 `docs/specs/04_*`（API 設計）定案；本文只規範能力與回應語意。

### US-010 staging 部署（P0）

- 身為驗收者，我想要有一個雲端 staging 環境可以用瀏覽器打開，以便我親自操作驗收。
- 驗收條件：
  - AC-010-1：Given 部署完成，When 我在自己的電腦用瀏覽器開啟 staging 網址，Then 清單頁正常載入且可執行 US-001 ~ US-007 的全部操作。
  - AC-010-2：Given staging 環境，When 我檢視網址列，Then 連線為 HTTPS（見 NFR-002）。
  - AC-010-3：Given 一次新的部署完成，When 我重新整理頁面，Then 先前建立的待辦資料仍存在（見 NFR-006）。
  - AC-010-4：Given 交付的 README 與部署文件，When 由未參與開發者依文件操作，Then 可在本機把應用跑起來，並可重現一次 staging 部署（憑證由使用者自行提供）。
  - AC-010-5：Given staging 服務，When 我呼叫健康檢查端點，Then 回應 200 並可據以判斷服務存活（見 NFR-003）。
- 備註／限制：雲端供應商與部署方式由 plan-sd 決定；憑證與雲端帳號由使用者提供，agent 不得索取或代填（Epic 限制）。staging 是否需存取保護見 Q-008。

### US-011 使用者註冊（P1）

- 身為新使用者，我想要用帳號與密碼註冊，以便擁有屬於自己的待辦清單。
- 驗收條件：
  - AC-011-1：Given 我在註冊畫面，When 我輸入未被使用過的帳號識別（Email）與符合規則的密碼並送出，Then 帳號建立成功，我被導向登入後的清單頁或登入畫面。
  - AC-011-2：Given 我輸入的帳號識別已被註冊，When 我送出，Then 系統不建立帳號並顯示可讀的錯誤訊息。
  - AC-011-3：Given 我輸入不符合規則的密碼（長度不足，規則見 Q-009 裁決值，暫定至少 8 字元），When 我送出，Then 系統不建立帳號並顯示密碼規則錯誤訊息。
  - AC-011-4：Given 帳號建立成功，When 檢視儲存內容，Then 密碼以單向雜湊儲存，資料庫中查不到明文密碼（見 NFR-002）。
  - AC-011-5：Given 註冊失敗的任一情況，When 我檢視回應，Then 錯誤訊息不洩漏系統內部細節（堆疊、SQL、路徑）。
- 備註／限制：Email 驗證、密碼重設、第三方登入為範圍外。

### US-012 使用者登入與登出（P1）

- 身為已註冊使用者，我想要登入取得憑證並能登出，以便安全地存取自己的待辦。
- 驗收條件：
  - AC-012-1：Given 我已註冊，When 我以正確帳密登入，Then 系統回傳 JWT，且我可進入清單頁。
  - AC-012-2：Given 我輸入錯誤密碼或不存在的帳號，When 我送出登入，Then 系統回應 401 並顯示不區分「帳號不存在／密碼錯誤」的統一錯誤訊息。
  - AC-012-3：Given 我持有有效 JWT，When 我呼叫受保護的待辦 API，Then 請求成功。
  - AC-012-4：Given 我未帶 JWT 或帶入無效／過期的 JWT，When 我呼叫受保護的待辦 API，Then 系統回應 401，且不回傳任何待辦資料。
  - AC-012-5：Given 我已登入，When 我點擊登出，Then 用戶端持有的憑證被清除，再次開啟清單頁時需重新登入。
- 備註／限制：JWT 有效期、是否提供 refresh token 見 Q-010。

### US-013 使用者資料隔離（P1）

- 身為已登入使用者，我想要只看到並只能操作自己的待辦，以便我的資料不被他人看到或改動。
- 驗收條件：
  - AC-013-1：Given 使用者 A 與 B 各自建立了待辦，When A 登入後開啟清單頁，Then 只列出 A 的待辦，完全不含 B 的任何待辦。
  - AC-013-2：Given A 已登入且知道 B 的某筆待辦識別碼，When A 以自己的憑證讀取、更新、切換或刪除該筆，Then 系統回應 404 或 403 且該筆資料未被改動。
  - AC-013-3：Given 任一待辦，When 檢視其資料，Then 它明確歸屬於一個使用者。
  - AC-013-4：Given 篩選與清單查詢，When 由任一使用者執行，Then 結果均先以其身分過濾後再套用狀態篩選。
- 備註／限制：P0 階段無使用者概念，P0 既有資料於導入 P1 時的歸屬處理見 Q-011。

## 7. 名詞定義

| 名詞 | 定義 |
|---|---|
| 待辦（Todo） | 使用者建立的一筆事項，具備：唯一識別碼、標題、完成狀態（已完成／未完成）、建立時間；（P1 起）所屬使用者。 |
| 完成狀態 | 布林值。未完成 = 尚待處理；已完成 = 已處理完畢。可雙向切換（US-005）。 |
| 建立時間 | 待辦被成功建立的時間點，建立後不因任何編輯而改變。 |
| 清單頁 | 應用的唯一頁面，同時承載新增、清單、篩選與各筆操作（US-008）。 |
| 篩選 | 依完成狀態限制清單顯示範圍，固定三種：全部／未完成／已完成（US-006）。 |
| P0 / P1 / P2 | P0＝沒有就不能上線；P1＝P0 之後的次要優先；P2＝本 Epic 未使用。 |
| staging | 供驗收者以瀏覽器實際操作的雲端環境，非正式生產環境（US-010）。 |
| JWT | JSON Web Token，P1 登入後核發、用於呼叫受保護 API 的憑證（US-012）。 |
| 資料隔離 | 每位使用者只能讀寫自己建立的待辦（US-013）。 |
| UAT | 使用者驗收測試，由驗收者依 P0 使用者故事逐條於 staging 操作確認。 |
