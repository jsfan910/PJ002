## 1. 目標與範圍

### 1.1 目標

建立一套可重複使用的「AI Agent 軟體開發團隊」運作框架，讓規劃、開發、測試三組團隊能：

1. 在**不同 session** 中並行作業，僅靠檔案交接即可接手，不依賴對話記憶。
2. 每個階段產出**固定格式的規格文件**，作為下游的唯一輸入。
3. 派工、進度、審核、退回都留下**可檢視的紀錄**。
4. 依工作性質使用**適當等級的模型**，兼顧品質與成本。
5. 團隊內自主完成一整輪工作，只在「有結果」或「卡關 3 輪」時才請使用者介入。

### 1.2 範圍

- 本計畫書定義的是**框架**（角色、文件、流程、目錄、模板、agent 定義），不綁定特定專案的技術棧。
- 技術棧（語言、框架、雲端平台）由每個專案的系統設計階段依需求決定，並記錄於架構決策紀錄（ADR）。CI/CD 預設 GitHub Actions，可於 ADR 覆寫。

### 1.3 運作前提

- 每個 agent 的 session 是**獨立且無記憶**的。所有必要脈絡都必須在任務卡與交接文件內，這是本框架的第一設計原則。
- Leader 是**唯一決策者與唯一對使用者的窗口**。團隊成員不直接向使用者提問，遇到無法決定的事寫入任務卡 `blocked_reason`，由 Leader 處理。
- 所有紀錄以 Markdown 存放於專案目錄，可用 git 追蹤（建議 `git init`，見第 10 章）。

## 2. 團隊架構

```
                     ┌──────────────────────┐
                     │   使用者（最終審核）    │
                     └──────────┬───────────┘
                                │ 審核點 ①②③ / 升級單
                     ┌──────────┴───────────┐
                     │  Leader（Fable 5.1）   │  派工、協調、Gate 審核、最終決策
                     └──┬────────┬────────┬─┘
            ┌───────────┘        │        └───────────┐
   ┌────────┴────────┐  ┌───────┴────────┐  ┌────────┴────────┐
   │    規劃團隊       │  │    開發團隊      │  │    測試團隊       │
   │ BA / SA / SD     │  │ TL / BE / FE /  │  │ QA-Lead / CR /  │
   │                  │  │ DevOps          │  │ AT / UAT        │
   └──────────────────┘  └─────────────────┘  └─────────────────┘
        產出規格包              產出可運行程式           產出測試與審查報告
```

### 2.1 Leader（本 session）

| 職責 | 說明 |
|---|---|
| 需求受理 | 將使用者需求轉為 Epic 與第一批任務卡 |
| 派工 | 建立任務卡、指定角色與模型、設定依賴與驗收條件 |
| Gate 審核 | Gate 1（規格包）、Gate 2（可運行程式）先由 Leader 審，再呈使用者 |
| 仲裁 | 3 輪不過的任務卡由 Leader 裁決；無法裁決者寫升級單呈使用者 |
| 紀錄 | 維護 `tasks/_todo.md`、`tasks/_done.md`、日報、交接 |

### 2.2 規劃團隊（Planning）

| 角色 | 代號 | 職責 | 輸入 | 輸出 |
|---|---|---|---|---|
| 需求分析師 | `plan-ba` | 需求澄清、使用者故事、驗收條件、範圍界定 | 使用者原始需求、Leader 的 Epic 說明 | 需求規格書（SRS）、需求澄清紀錄 |
| 系統分析師 | `plan-sa` | 使用案例、領域模型、資料流、業務規則、介面清單 | SRS | 系統分析書 |
| 系統設計師／架構師 | `plan-sd` | 架構、模組設計、API 規格、資料庫 schema、部署架構、技術選型 | SRS + 系統分析書 | 系統設計書、API 規格（OpenAPI）、ADR、部署架構 |

團隊內審核：SA 審 BA 的 SRS，SD 審 SA 的分析書，BA 反向審 SD 的設計書是否覆蓋所有使用者故事（可追溯矩陣）。

### 2.3 開發團隊（Development）

| 角色 | 代號 | 職責 | 輸入 | 輸出 |
|---|---|---|---|---|
| 技術負責人 | `dev-tl` | 將設計書拆成開發工作項（WBS）、定義分支策略、整合、解決技術衝突 | 規格包 | 開發計畫（WBS）、README、CHANGELOG |
| 後端工程師 | `dev-be` | API、商業邏輯、資料層、單元測試 | WBS 工作項、API 規格、schema | 可通過單元測試的後端程式碼 |
| 前端工程師 | `dev-fe` | UI、狀態管理、與 API 串接、元件測試 | WBS 工作項、API 規格、UI 需求 | 可通過元件測試的前端程式碼 |
| DevOps 工程師 | `dev-ops` | CI pipeline、容器化、雲端部署（IaC）、環境變數、回滾程序 | 部署架構、ADR | CI/CD 設定、IaC、部署文件、staging 環境網址 |

團隊內審核：TL 對每個工作項做初審（能否 build、測試是否通過、是否符合 API 規格），不過直接退回，不進測試團隊。

### 2.4 測試團隊（QA）

| 角色 | 代號 | 職責 | 輸入 | 輸出 |
|---|---|---|---|---|
| 測試負責人 | `qa-lead` | 測試策略、測試計畫、測試案例設計、缺陷分級、最終測試報告 | 規格包 | 測試計畫、測試案例、測試報告 |
| 程式碼審查員 | `qa-cr` | 靜態審查：正確性、安全性、可維護性、是否符合設計書 | 程式碼、設計書 | Code Review 報告（含阻擋級／建議級） |
| 自動化測試工程師 | `qa-at` | 整合測試、E2E 測試、效能與安全掃描的自動化 | 測試案例、staging 環境 | 自動化測試程式碼、執行結果 |
| 使用者測試代理人 | `qa-uat` | 以終端使用者視角依使用者故事逐一操作驗證 | SRS 使用者故事、staging 環境 | UAT 報告、缺陷清單 |

團隊內審核：QA-Lead 彙整 CR / AT / UAT 結果，決定「通過／退回開發」。

**寫入權責（避免並行衝突）**：

| 路徑 | 可寫入者 |
|---|---|
| `tasks/T-*.md` frontmatter 的 `status`/`round` | 該卡 assignee、審核者、Leader |

| `docs/specs/*` | 規劃團隊對應角色；開發／測試只能提出「規格變更請求」任務卡 |
| `src/*` | 開發團隊，每張任務卡一個分支 `task/T-####-{slug}` |
| `tests/*` | 開發（單元）與測試團隊（整合／E2E），以子目錄區分 |
| `worklog/handoff/*` | 每個檔案只由其產生者寫入 |

## 5. 模型等級配置

### 5.1 判準

| 工作性質 | 模型 | 理由 |
|---|---|---|
| 高歧義、跨文件推理、決策與仲裁、需要「看出遺漏」 | **Opus 5**（`claude-opus-5`） | 規格與審查的錯誤成本最高，下游全部受影響 |
| 產出量大、規格已明確、需要穩定執行 | **Sonnet 5**（`claude-sonnet-5`） | 開發與自動化測試的主力，性價比最佳 |
| 機械性、格式化、單一明確步驟 | **Haiku 4.5**（`claude-haiku-4-5`） | 看板彙整、格式檢查、UAT 逐步操作 |
| 全局協調、跨團隊仲裁、面對使用者 | **Fable 5.1**（`claude-fable-5-1`） | Leader，本 session |

### 5.2 角色配置表（建議「平衡模式」）

| 角色 | 平衡模式（建議） | 品質模式 | 省錢模式 | 說明 |
|---|---|---|---|---|
| Leader | Fable 5.1 | Fable 5.1 | Opus 5 | 已是本 session |
| plan-ba | Opus 5 | Opus 5 | Sonnet 5 | 需求歧義最大 |
| plan-sa | Opus 5 | Opus 5 | Sonnet 5 | 跨文件一致性 |
| plan-sd | Opus 5 | Fable 5.1 | Opus 5 | 架構決策影響最深，不建議降級 |
| dev-tl | Opus 5 | Opus 5 | Sonnet 5 | 拆工與整合需要全局判斷 |
| dev-be | Sonnet 5 | Opus 5 | Sonnet 5 | 主力產出 |
| dev-fe | Sonnet 5 | Opus 5 | Sonnet 5 | 主力產出 |
| dev-ops | Sonnet 5 | Opus 5 | Sonnet 5 | 設定檔多、規格明確 |
| qa-lead | Opus 5 | Opus 5 | Sonnet 5 | 決定通過與否 |
| qa-cr | Opus 5 | Fable 5.1 | Sonnet 5 | 審查品質直接決定缺陷漏網率 |
| qa-at | Sonnet 5 | Sonnet 5 | Sonnet 5 | 測試程式碼產出 |
| qa-uat | Haiku 4.5 | Sonnet 5 | Haiku 4.5 | 逐步操作、對照預期結果 |

### 5.3 定價參考（Anthropic 第一方 API，每百萬 token）

| 模型 | 輸入 | 輸出 |
|---|---|---|
| Fable 5.1 | $10.00 | $50.00 |

### 5.4 動態升級規則

- 任何任務卡進入**第 3 輪**時，自動將該卡的模型升一級（Haiku→Sonnet→Opus→Fable），並在任務卡記錄。
- 效能等級（effort）：Opus / Sonnet 預設 `high`；規劃團隊與 qa-cr 用 `xhigh`；qa-uat 用 `medium`。

## 6. 交接文件定義（跨 session 協作的核心）

### 6.1 任務卡（Task Card）— 派工單兼狀態事實來源

路徑：`tasks/T-####-{slug}.md`

```markdown
---
id: T-0012
title: 實作使用者登入 API
epic: E-001
team: dev              # plan | dev | qa
role: dev-be
model: sonnet          # haiku | sonnet | opus | fable
status: in_progress    # todo | in_progress | review | rework | blocked | done | cancelled
round: 1               # 目前第幾輪（1..3）
depends_on: [T-0008, T-0010]
inputs:
  - docs/specs/04_API規格.yaml#/paths/~1auth~1login
  - docs/specs/05_資料庫設計.md#users
outputs:
  - src/auth/login.py
  - tests/unit/test_login.py
acceptance:
  - 單元測試覆蓋率 ≥ 80%
  - 通過 API 規格的 contract test
  - qa-cr 阻擋級發現 = 0
reviewer: dev-tl
branch: task/T-0012-login-api
```

### 6.2 工作紀錄＋交接文件（Worklog / Handoff）— 同一檔，開工寫上半，完工寫下半

路徑：`worklog/handoff/yyyymmdd-HHmm-T####-r{n}-{role}.md`（時間為開工時間）

```markdown
# T-0012 r1 — dev-be — 工作紀錄與交接

## A. 開工紀錄（開工時立即寫）
- 開工時間：
- 角色／模型：dev-be / sonnet
- 讀取的輸入：（列出實際讀過的檔案與段落）
- 本輪計畫：（3–7 條）
- 預期產出：

## B. 交接（完工或中止時寫）
- 完工時間／狀態：done | review | blocked
- 完成事項：
- 產出物（路徑）：
- 未完成／已知問題：
- 我做的假設與決策（含理由）：
- 驗證方式（接手者如何確認我做的是對的——指令與預期結果）：
- 下一步建議：
- 需要 Leader 裁決的事：（無則寫「無」）
```

**判準**：換一個 agent 明天早上只讀「任務卡 + 本檔 B 段」，能不能直接開工？不能就是還沒交接完。

### 6.3 審核紀錄（Review Record）

寫入任務卡的「審核紀錄」表 + 產生一份 `worklog/handoff/…-{reviewer}.md`（B 段填審核發現）。Code Review 報告另依 4.3 產出到 `docs/reports/`。

### 6.4 升級單（Escalation）— 給 Leader，Leader 再彙整給使用者

路徑：`docs/reports/yyyymmdd-HHmm-升級-T####.md`。固定五段：

1. **核心爭議**：具體卡關點與實質影響，先講結論與後果。
2. **證據觀點**：考量的規範、證據、已嘗試的做法（3 輪各做了什麼）。
3. **選項**：最多 3 個，各寫「做法／代價」。
4. **建議 + 一句理由**。
5. **推翻成本**：選錯了要付什麼、能不能回頭。

### 6.5 Gate 報告（給使用者審核）

路徑：`docs/reports/yyyymmdd-HHmm-Gate{1|2}-{Epic}.md`。內容固定：

1. 結論（通過／有條件通過／不通過）
2. 重點摘要（只寫會改變使用者判斷的事，沒有寫「無」）
3. 需要使用者裁決的項目（五段格式，沒有寫「無」）
4. 完整文件連結清單

## 7. 派工與交接流程

### 7.1 主流程

```
使用者需求
   │
   ▼
[Leader] 建 Epic + 規劃任務卡 (T-plan-*)          ── 記錄：tasks/, _todo.md
   │
   ▼
[規劃團隊] BA → SA → SD（各自 session，串行有依賴）
   │   內部審核：SA審SRS、SD審SA、BA審追溯矩陣，每卡 ≤3 輪
   ▼
[Leader] Gate 1 預審 → 產 Gate1 報告 ─────────────▶ 【使用者審核 ②】
   │                                                     │ 通過
   ▼◀────────────────────────────────────────────────────┘
[Leader] 建開發任務卡（依 dev-tl 的 WBS）
   │
   ▼
[開發團隊] TL 拆工 → BE / FE / Ops 平行開發（各自分支）
   │   內部審核：TL 初審（build + 單元測試 + 規格符合），每卡 ≤3 輪
   │   Ops：CI 綠燈 + 部署 staging
   ▼
[測試團隊] CR + AT + UAT 平行 → QA-Lead 彙整
   │   不通過 → 產缺陷清單 → Leader 建修正任務卡 → 回開發（計入回合）
   │   通過 → 測試總結報告
   ▼
[Leader] Gate 2 預審 → 產 Gate2 報告 ─────────────▶ 【使用者審核 ③】
```

### 7.2 任務卡狀態機

```
todo ──▶ in_progress ──▶ review ──┬──▶ done
  ▲                        │       │
  │                        │       └──▶ rework ──▶ in_progress (round+1)
  │                        │
  │                        └──▶ blocked ──▶ (Leader 裁決) ──▶ in_progress | cancelled
  │
  └── Leader 建卡
```

- `round` 每次進入 `rework` 時 +1。`round` 達 3 且仍未通過 → 自動 `blocked`，`blocked_reason` = "3輪未過"，觸發升級單。
- 所有狀態變更必須同時：更新任務卡 frontmatter `status`/`updated` + 寫交接檔 B 段 + （Leader）更新看板。

### 7.3 派工方式

**方式 A（主要）：Leader session 以子代理派工**

- Leader 讀任務卡 → 以 Agent 工具啟動對應 `.claude/agents/{role}.md`，提示詞只給：任務卡路徑、必讀的輸入路徑、要求「開工先寫 worklog A 段，完工寫 B 段並更新任務卡」。
- 無依賴的任務卡一次平行啟動（例如 BE / FE / Ops，或 CR / AT / UAT）。
- 子代理回報只是摘要；**Leader 以任務卡與交接檔為準**，不以子代理口頭回報為準。

**方式 B（備援）：獨立 session 接手**

- 使用者在任意 session 輸入 `/takeover T-0012`，該 skill 會：讀任務卡、讀最近一份交接檔、載入對應角色定義、寫 worklog A 段，然後開工。
- 適用：Leader session 已滿、需要人為介入觀察、或要換模型重跑。

兩種方式共用同一套檔案協定，紀錄格式完全相同。

### 7.4 並行規則

1. 只有 `depends_on` 全為 `done` 的卡才可啟動。
2. 兩張 `in_progress` 的卡 `outputs` 不得重疊（Leader 建卡時檢查）。
3. 程式碼每卡一分支，合併由 dev-tl 執行，合併訊息含任務卡 ID。
4. 規格文件在 Gate 1 通過後凍結；變更需走「規格變更請求」任務卡（plan 團隊處理，Leader 核准）。

### 7.5 使用者介入點（只有這些）

| 時機 | 使用者看到什麼 | 使用者要做什麼 |
|---|---|---|
| ① 計畫書 | 本文件 | 確認／修改 |
| ② Gate 1 | Gate1 報告 + 規格包連結 | 通過／退回（附意見） |
| ③ Gate 2 | Gate2 報告 + staging 網址 + 測試總結 | 驗收／退回（附意見） |
| 升級單 | 五段式升級報告 | 裁決選項 |

其餘一律團隊內自行解決，使用者可隨時看 `tasks/_todo.md` 與 `worklog/handoff/` 了解進度，但不需要回應。

## 9. 實作步驟（確認後執行）

### Phase 0：框架建置（Leader 自行完成，約 1 個工作階段）

1. `git init`（若使用者同意），建立 `.gitignore`。
2. 建立第 3 章目錄骨架。
3. 撰寫 `docs/templates/`：任務卡、工作紀錄／交接、升級單、Gate 報告、SRS、SA、SD、ADR、測試計畫、測試案例、CR 報告、UAT 報告、測試總結。
4. 撰寫 `.claude/agents/` 12 個角色定義（含模型、可用工具、角色提示詞：職責、必讀、必寫、DoD、禁止事項）。
5. 撰寫 `.claude/skills/`：`dispatch`、`handoff`、`review-round`、`takeover`。
6. 更新 `CLAUDE.md`：新增「協作協定摘要」段落（狀態機、寫入權責、回合規則），並將 CLAUDE_bak.md 中的「回報規則」納入（與第 6.5 一致）。
7. 建立 `tasks/_todo.md`、`tasks/_done.md`、`docs/archive/_index.md`。

**交付物**：可用的框架 + 一份 `docs/reports/…-Phase0-完成報告.md` 請使用者審核。

### Phase 1：試跑（Dry Run）

以一個小型範例需求（第 10 章第 5 項）走完整流程一次，驗證：

- 三個團隊能只靠檔案接手。
- 3 輪規則與升級單真的會觸發並正確記錄。
- Gate 1 / Gate 2 報告格式對使用者可讀。

**交付物**：Gate 1 報告 → 使用者審核 → Gate 2 報告 + 可運行程式 → 使用者審核。

### Phase 2：修正框架

依試跑發現修正模板、agent 提示詞與流程，沉澱到 CLAUDE.md「工作鐵則」。

## 11. 風險與對策

| 風險 | 對策 |
|---|---|
| Agent 宣稱「完成」但實際未驗證 | 交接檔強制「驗證方式」欄；審核者必須實際執行該驗證，不採信口頭 |
| 跨 session 脈絡遺失 | 任務卡 `inputs` 精確到段落錨點；交接檔「假設與決策」欄強制填寫 |
| 平行寫入衝突 | `outputs` 不重疊檢查 + 每卡一分支 + 看板只有 Leader 寫 |
| 規格在開發中被默默改掉 | Gate 1 後凍結；變更走規格變更請求卡 |
| 成本失控 | 平衡模式 + 動態升級只在第 3 輪；Leader 每日在日報記錄各卡回合數 |
| 3 輪規則導致無限升級 | 升級單五段式強制寫「推翻成本」，使用者一次裁決即定案 |

## 附錄 A：名詞

- **Epic**：一個使用者需求的整體單位，含多張任務卡。
- **Gate**：需要使用者審核的關卡。Gate 1 = 規格包，Gate 2 = 可運行程式。
- **回合（round）**：一張任務卡從「做」到「審」的一次循環。
- **規格包**：4.1 全部文件的集合。
